# Архитектура NutriFlow

Обозначения: «сейчас» подтверждается исходниками; «рекомендация» ещё не реализована и требует согласования. Этот документ не является поручением переписать проект.

## .NET, MAUI и ASP.NET Core — не одно и то же

- C# — язык, на котором написана логика.
- .NET — платформа, библиотеки, runtime и инструменты сборки.
- .NET MAUI — экраны мобильного приложения, навигация и доступ к возможностям телефона.
- ASP.NET Core — отдельное серверное приложение, принимающее HTTP-запросы.
- SQLite — локальный файл базы; наличие базы не означает наличие удалённого сервера.

MAUI не является нашим бэкендом. У автономного APK бизнес-логика и SQLite находятся на телефоне; это не запуск ASP.NET внутри Android. [Назначение MAUI](https://learn.microsoft.com/en-us/dotnet/maui/what-is-maui?view=net-maui-10.0).

## Действующие проекты

| Проект | Где исполняется / зачем нужен |
| --- | --- |
| `NutriFlow.Domain` | Общая обычная .NET-библиотека: значения КБЖУ, блюда, порции, состояния и расчётные правила |
| `NutriFlow.Infrastructure` | Общая .NET-библиотека: EF Core / SQLite, хранилища, Groq и другие адаптеры, продукты, файлы |
| `NutriFlow.Api` | Отдельный ASP.NET Core процесс: HTTP, DI, workflow и временный веб-клиент |
| `mobile/NutriFlow.Mobile.Core` | Обычная .NET-библиотека: локальные профили, координация автономных сценариев и прямых интеграций |
| `mobile/NutriFlow.Mobile` | MAUI-приложение: отображение, действия, камера, микрофон, защищённое хранение ключа |
| `NutriFlow.Console` | Отдельный консольный сценарий расчётов; не библиотека мобильного интерфейса |
| `NutriFlow.Tools` | Offline-инструменты резервных копий серверного хранилища; мобильного экспорта ими пока нет |
| Проекты `.Tests` / `scripts/tests` | Проверки домена, SQLite / HTTP, мобильного ядра и сборочных / клиентских скриптов |

Направление ссылок `.csproj`:

```text
Mobile → Mobile.Core → Infrastructure → Domain
Api ────────────────→ Infrastructure → Domain
Api ────────────────────────────────→ Domain
Console ────────────────────────────→ Domain
Tools ──────────────→ Infrastructure → Domain
```

Domain не зависит от MAUI, EF Core / SQLite, HTTP и конкретных AI-провайдеров. Он содержит модель, расчётные правила и контракты разбора (`IMealParser`, `INutritionLabelReader`), а также демонстрационный `FakeMealParser`; настоящие сетевые адаптеры находятся в Infrastructure. Благодаря этому одни формулы используются на телефоне и в серверном варианте. Код экранов можно изменить без переписывания этих формул. Это не обещание, что любую библиотеку удастся напрямую перенести в Kotlin или Swift: при другом языке клиенту потребуется API либо отдельная интеграция / реализация.

Три solution группируют сборки, но не создают HTTP-соединения: `NutriFlow.sln` — восемь обычных / серверных проектов; `mobile/NutriFlow.Mobile.Core.slnx` — четыре проекта ядра и его тестов; `mobile/NutriFlow.Mobile.slnx` — MAUI с транзитивными ссылками. Реальные зависимости определены `ProjectReference`, а не расположением папок.

Временное техническое решение: Core через `Compile Link` включает восемь ASP.NET-независимых исходников из каталога API: workflow, его проверку / исключение и пять файлов DTO / преобразований. Они компилируются внутри Core; пространства имён `.Api.*` исторические. Перенос в общую application/contracts-библиотеку может упростить сопровождение, но сейчас не выполнен и не требуется ради документации.

## Текущий автономный поток

```text
Экран MAUI → LocalMealClient(зафиксированный GUID профиля)
           → отдельная SQLite + хранилища + общий workflow
           → Domain: состав / итоговая масса / порция
           → предпросмотр → подтверждение → дневник либо сохранённое блюдо
```

Для свободного текста, этикетки и аудио Core вызывает Groq напрямую по HTTPS с личным ключом. Поиск штрихкода сначала локальный, затем Open Food Facts. Обычный ручной ввод уже строит структурированный draft и AI не требует; offline-парсер не понимает произвольную речь вместо Groq.

`LocalProfileStore` хранит реестр / выбор профиля. База и фото: `FileSystem.AppDataDirectory/nutriflow/profiles/<Guid:N>/`. Ключ — `SecureStorage` с GUID профиля; модели и последний черновик — `Preferences`. На каждую операцию открывается контекст нужного файла SQLite; серверная рабочая база не используется.

Профили не защищены паролем друг от друга на разблокированном телефоне. Автоматический backup отключён, мобильного экспорта пока нет. Очистка данных / удаление приложения уничтожает локальные данные. Подтверждённая подпись APK нужна для обновления поверх существующей установки, не для входа в аккаунт.

## Почему нынешний UX неудобен

Сейчас пять разделов представлены горизонтально прокручиваемыми кнопками; интерфейс в основном строится C#-кодом в `MainPage` и её partial-файлах. Формы однотипны, список собирается внутри ScrollView, переход перерисовывает содержимое, многие операции блокируют весь экран. Это функциональный интерфейс проверки, не законченная мобильная дизайн-система.

UI — расположение и внешний вид элементов. UX шире: сколько действий нужно, понятны ли сообщения, можно ли исправить ошибку, продолжить ввод, не потерять прогресс и пользоваться одной рукой. Замена цветов сама по себе UX не исправляет.

MAUI позволяет менять страницы, стили, навигацию, графику и анимации, а handlers связывают общие controls с нативными и позволяют их настраивать. Это не гарантия отсутствия платформенных багов: сложные жесты, анимации, производительность списков и особенности Android / iOS надо проверять на устройстве. [Handlers и нативные controls](https://learn.microsoft.com/en-us/dotnet/maui/user-interface/handlers/?view=net-maui-10.0).

Рекомендация: сначала спроектировать 3–5 ключевых сценариев и проверить прототип в MAUI, а не менять стек из-за нынешних форм. Возможный порядок: дневник → единая заметная точка ввода → черновик → исправление / подтверждение; каталог и библиотека блюд — вспомогательные сценарии. Это предложение, не утверждённая навигация.

Помощь агента / дизайнера: сценарии, структура экранов, состояния loading / empty / error / offline, прототип, дизайн-токены, проверка текста / доступности и реализация. Отдельный UX-дизайнер и тесты с пользователями полезны; ещё один агент или специальный инструмент сами по себе не доказывают удобство. Переписывание на Kotlin / Swift рассматривать только при воспроизводимом ограничении MAUI, которое существенно важнее стоимости двух клиентов.

## Локальные данные, вход и синхронизация

Это независимые задачи:

1. Аутентификация: кто вошёл, например подтверждение Google.
2. Авторизация: какие записи ему разрешены.
3. Хранение / синхронизация: где дневник и как он попадает на другой телефон.
4. Монетизация: на что даёт право подписка и кто оплачивает AI.

Локальное приложение технически может использовать Google-вход. Но Google-вход не загружает нашу SQLite на другой телефон автоматически. Нужен отдельный backend, управляемое облачное хранилище или явно выбранный механизм backup / sync. Google подтверждает личность, а не бесплатно хранит произвольный дневник NutriFlow. При серверном входе полученное подтверждение проверяется сервером; присланный email / GUID не доказательство личности. [Google: проверка ID token сервером](https://developers.google.com/identity/sign-in/android/backend-auth), [актуальный Android Sign in with Google](https://developer.android.com/identity/sign-in/credential-manager-siwg).

| Режим | Офлайн-дневник | Перенос между телефонами | AI-ключ | Статус |
| --- | --- | --- | --- | --- |
| Локальные профили | Да | Нет встроенного переноса | Личный ключ пользователя | Реализован Android |
| Клиент → сервер | Зависит от отдельно реализованного кэша | Возможен после аккаунтов / server storage | Секрет сервера | API есть, публичные аккаунты нет |
| Local-first + облачные функции | Локальный дневник сохраняется | Через отдельно разработанный sync | Обычно серверный; BYOK может быть опцией | Рекомендация, не реализовано |

Рекомендуемое направление для массового продукта — последний вариант. Один ASP.NET Core сервис / модульное приложение достаточно; микросервисы не требуются. На телефоне — удобный UI, локальные данные и расчёты; на сервере — аккаунт, права, AI-шлюз, учёт расходов / подписки и выбранное облачное хранение. Это не означает необходимость сразу синхронизировать все фото или полностью менять СУБД.

Публичный API сейчас небезопасен как многопользовательский сервис: он выбирает одного локального владельца, не проверяет личность запросившего. Перед открытием нужны реальная auth / owner-проверка, HTTPS, защищённые секреты, резервные копии и тесты изоляции. `no-store`, rate limit и GUID не заменяют auth.

Sync не равен «добавить Google-кнопку»: понадобятся соответствие local profile ↔ account, явное согласие на загрузку существующих данных, версии / конфликты, повторы, удаления, восстановление, работа без сети и тесты двух устройств. Объединять аккаунты по одинаковому email или данные локальных профилей автоматически нельзя.

## Почему нельзя спрятать общий Groq-ключ в APK

Подпись APK подтверждает издателя / совместимость обновления. Она не шифрует встроенные секреты от владельца устройства. Постоянный общий ключ, попавший в приложение, надо считать извлекаемым; обфускация не делает такую схему надёжной.

Сейчас выбран BYOK: пользователь сам сохраняет личный ключ. Для обычного пользователя рекомендован серверный AI-шлюз с секретом в серверном хранилище, а приложение получает только ограниченный доступ NutriFlow. Даже если дневник остаётся локальным, сервер может обслуживать только AI / аккаунт: полное облачное хранение и сокрытие ключа — не одна задача. Провайдер также рекомендует не встраивать ключи в клиент и использовать доверенный backend. [Groq: Secure API Key Management](https://console.groq.com/docs/production-readiness/security-onboarding).

## Решения, которые пока открыты

- Утвердить UX и измерить сценарии на реальном Android.
- Выбрать, нужен ли облачный перенос в первой публичной версии; не отключать текущий офлайн-режим молча.
- Определить собственный / управляемый backend, способ входа, страны размещения и требования к персональным данным.
- Определить политику local profile → account, конфликтов и backup до миграции.
- Проверить стоимость AI на реальных анонимизированных сценариях до назначения цены и квоты.
- Проверить новый iOS-граф и UX отдельно; кроссплатформенные исходники не равны проверенным приложениям на двух ОС.
