# Навигация по коду

## Запуск API

Начальная точка — `NutriFlow.Api/Program.cs`. В нём виден порядок регистрации сервисов, настройки HTTP и подключения маршрутов.

`Program` сначала читает `Demo:SeedData` как `bool`, затем `ServiceRegistration` проверяет выбор AI и наличие требуемого ключа, и только после этого настраивает хранилище. Флаг демо передаётся в `ApplicationSetup` уже прочитанным значением. Общий `appsettings.json` не включает демо и не выбирает AI; отдельный `appsettings.Development.json` задаёт прежний локальный сценарий. Production требует явной настройки провайдера.

- `Configuration/ServiceRegistration.cs` — зависимости, пути хранения, HTTP-клиенты, выбор AI-провайдера и ограничитель запросов.
- `Configuration/OpenApiConfiguration.cs` — только метаданные: формат `decimal`, различие числового ввода / вывода и строковые defaults двух enum-полей; сериализатор HTTP не меняется.
- `Configuration/ApplicationSetup.cs` — единая политика HTTP-кэша `/api`, обработка ошибок, применение миграций и однократный перенос старых фото при включённой настройке, демо-наполнение, защитные заголовки, статические файлы, Swagger и health checks.
- `Endpoints/MealSessionEndpoints.cs` — создание, чтение, дополнение, подтверждение сессии и отдельный разбор черновика.
- `Endpoints/SavedDishEndpoints.cs` — список личных сохранённых блюд и чтение их состава и пищевой ценности.
- `Endpoints/DailyDiaryEndpoints.cs` — дневные цели и прогресс.
- `Endpoints/MealEntryEndpoints.cs` — чтение, исправление массы и мягкое удаление порции, проверка `If-Match` и выдача `ETag`.
- `Endpoints/ProductEndpoints.cs` — продукты, штрихкоды и алиасы.
- `Endpoints/MediaEndpoints.cs` — расшифровка аудио, анализ и выдача фотографий.

Каждый файл endpoints сначала регистрирует маршруты, затем содержит их обработчики. URL, имена операций и JSON-контракты при разделении не менялись.

В начале `ConfigureNutriFlowAsync` middleware регистрирует `Response.OnStarting` для сегмента `/api` и выставляет `Cache-Control: private, no-store` непосредственно перед отправкой заголовков. Регистрация находится перед обработчиком исключений, поэтому правило действует и после очистки ответа при `500`, а также для ошибок привязки, ограничения запросов и неизвестных API-маршрутов. Заголовок не дублируется в обработчиках порций и фото; `ETag`, `If-Match` и диапазонная выдача фотографий сохраняются. Внешние маршруты, включая статические файлы, Swagger и health checks, не затронуты. Порядок вызовов описан в [документации OnStarting](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.http.httpresponse.onstarting?view=aspnetcore-10.0).

## От запроса к расчёту

```text
Program → Endpoints → MealWorkflowService
                          ├─ IMealParser → структурированный MealDraft
                          ├─ LocalProductCatalog → доступные продукты
                          ├─ Domain → расчёты КБЖУ
                          ├─ MealSessionStore → сохранённый предпросмотр
                          ├─ DailyDiaryStore → подтверждённые порции (Diary)
                          └─ SavedDishStore → сохранённое блюдо (CreateDish)
```

`Services/MealWorkflowService.cs` проверяет сообщения, передаёт парсеру назначение сессии и доступные владельцу названия блюд, разрешает продукты, строит предпросмотр и проверяет его версию. `Diary` подтверждает съеденные порции, `CreateDish` — одно приготовленное блюдо без записи в дневник. Повторяющиеся продукты разрешаются один раз внутри одного расчёта, но заново при следующем запросе. При естественном упоминании сохранённого блюда используются его ранее рассчитанные КБЖУ и качество, а не арифметика AI.

`Services/MealPreviewValidator.cs` проверяет вложенный сохранённый JSON до преобразования в DTO: структуру, обязательные поля КБЖУ, допустимые значения и названия качества. Проверка не пересчитывает исторический результат и допускает отсутствующие поля старого формата.

`Contracts` содержит тела запросов и ответов, включая `Purpose` сессии и сохранённые блюда. `DailyProgressResponse.cs` также содержит `UpdateMealEntryRequest` и ответ порции с `id` / `revision`. `ResponseMapper.cs` преобразует доменные продукты, КБЖУ, сохранённые порции и блюда в ответы API; бизнес-арифметики в нём нет.

Исправление дневника проходит напрямую из `MealEntryEndpoints` в `DailyDiaryStore`, без повторного разбора AI. `GET /api/meal-entries/{id}` возвращает активную порцию и её ревизию в `ETag`; `PUT` и `DELETE` требуют эту ревизию в `If-Match`. Ошибки различают отсутствующий заголовок (`428`), неверный формат (`400`), конфликт ревизии (`412`) и недоступную запись (`404`). Чтение и успешное исправление имеют `Cache-Control: private, no-store`.

## Домен и хранение

`NutriFlow.Domain` не зависит от HTTP, EF Core или AI-провайдера. Для расчётов начни с `NutritionValues`, затем `DishIngredient`, `DishBatch`, `MealEntry`, `DailyProgress`. Для ввода — `CaptureSession`, `MealSessionPurpose`, `MealDraft`, `DishDraft`, `IngredientDraft`, `PortionDraft`. Назначение `Diary` / `CreateDish` не является состоянием сессии: назначение неизменно, состояние меняется при сборе и подтверждении.

`MealEntry.WithWeight` создаёт новую порцию пропорционально переданной массе и сохраняет консервативное качество КБЖУ. Хранилище каждый раз вызывает его на исходном снимке, а не на результате прошлой правки; цепочка исправлений не накапливает промежуточное округление. Для качества новой массы допустимы только `Exact` и `Estimated`.

`NutriFlow.Infrastructure` содержит реализации внешних вызовов и хранения:

- `LocalProductCatalog` — личные и общие продукты, поиск, алиасы и повышение качества;
- `ProductLookupService` / `ExternalProducts` — local-first поиск по штрихкоду и внешний импорт;
- `MealSessionStore` — сессии с назначением, версии и ключи безопасных повторов;
- `MealDraftSerializer` — формат сохранённого JSON-черновика и восстановление доменных объектов с проверкой их ограничений;
- `DailyDiaryStore` — цели, атомарная запись порций из дневниковой сессии, чтение активных записей, исправление массы и мягкое удаление с проверкой ревизии;
- `StoredMealEntry` — ID, ревизия, дата, исходная сессия и текущая доменная порция; `MealEntryChangeResult` — результат изменения или конфликта;
- `SavedDishStore` / `StoredSavedDish` — личные сохранённые блюда, поиск по имени и атомарное подтверждение `CreateDish` без записи порций;
- `LabelPhotos/LabelPhotoStore` — запись файлов и метаданных, чтение только фотографий владельца;
- `LabelPhotos/LegacyLabelPhotoImporter` — однократная регистрация прежних снимков за локальным владельцем без изменения ссылок;
- `Persistence` — EF-модель и история миграций;
- `Ai`, `Audio`, `LabelPhotos` — транспорт, проверка входных данных и файлов.

`Persistence/SavedDishRecord.cs` и таблица `SavedDishes` хранят имя, итоговую массу, КБЖУ на 100 г и качество, владельца и ссылку на исходную подтверждённую сессию. Её неизменяемый предпросмотр сохраняет состав и первоисточники; изменения каталога не переписывают этот снимок. Для повторного расчёта блюдо проецируется в `Product` с источником `SavedDish`, не создавая строку в каталоге продуктов. Это снимок приготовленного блюда, не шаблон рецепта и не учёт оставшегося запаса еды.

`Persistence/MealEntryRecord.cs` и таблица `MealEntries` сохраняют исходные подтверждённые порции. `Persistence/MealEntryAdjustmentRecord.cs` и таблица `MealEntryAdjustments` хранят одно текущее исправление или отметку удаления на запись, не меняя оригинал. Владение проверяется через подтверждённую сессию `Diary`. Без исправления ревизия равна `0`; изменение начинается с транзакции до чтения и повышает ревизию. Дневной прогресс и ответы подтверждения показывают активные исправленные порции, но прежний предпросмотр сессии остаётся неизменным. Повторное подтверждение не восстанавливает удалённые порции.

## Где проверять поведение

- `NutriFlow.Domain.Tests` — формулы, ограничения и неизменяемость модели.
- `NutriFlow.Infrastructure.Tests` — SQLite, владельцы, миграции, транзакции и внешние ответы на управляемых заменах HTTP.
- `NutriFlow.Api.Tests` — реальный ASP.NET Core pipeline с временной базой, маршруты, JSON, ошибки и повторы.
- `scripts/tests` — запись голоса / состояние временного клиента с заменами браузерных API и управление iOS smoke-проверкой с заменами Apple-команд.
- `scripts/Test-MealWorkflow.ps1` — HTTP-сценарий через отдельный Kestrel-процесс: искусственная база, Fake, создание / повторное использование блюда, дробные порции, повторы и перезапуск.

В отличие от `WebApplicationFactory` / `TestServer`, этот PowerShell-скрипт запускает уже собранную DLL через `dotnet` и обычный сетевой сокет. Он проверяет границу процесса и сохранение данных между двумя запусками. Новый частный content root и ранние аргументы конфигурации отделяют проверку от рабочей установки; только дочерний процесс получает очищенное окружение. Сборка не выполняется скрытно, настоящий AI не подключается, искусственное хранилище остаётся для осмотра. Команда добавлена в CI; ограничения и ручная приёмка описаны в [MOBILE_API.md](MOBILE_API.md).

`MobileApiContractTests` проверяет фактические HTTP-ответы и JSON-форматы. `MobileOpenApiContractTests` отдельно сверяет 21 операцию `/api`, имена операций, основные схемы, строковые enum, nullable-поля, даты, идентификаторы и загрузку этикетки в генерируемом OpenAPI. Для чтения документа и capabilities достаточно временного сервера без миграций, демо и создания файла SQLite. `OpenApiMetadataApiTests` покрывает оба тела `409` подтверждения, фото `200` / `206` / пустой `416`, четыре ошибки `415`, defaults enum и различие числовых схем запроса / ответа. Приём чисел / числовых строк и реальный `416` проверяются на искусственной временной базе. Эти тесты не вызывают настоящий Groq и не проверяют генератор мобильного SDK; правила клиента перечислены в [MOBILE_API.md](MOBILE_API.md).

Большинство ответов описывается `.Produces` / `.ProducesProblem` рядом с маршрутом. Для второго MIME с другой схемой у одного `409` применяется только локальный `AddOpenApiOperationTransformer`: он дополняет `application/problem+json`, сохраняя прежний `application/json`. Файлы описываются типом `Stream`, который установленный генератор распознаёт как двоичный ответ. Трансформер схем использует `ParameterDescription` для различия ввода / вывода; текущие DTO не разделяются между запросами и ответами. При будущем повторном использовании одного DTO в обе стороны обязательно перепроверить схемы, а не считать такое разделение автоматическим.

Сценарий сохранения и повторного использования блюда покрывают `SavedDishStoreTests`, `SavedDishWorkflowApiTests`, `CaptureSessionPurposeTests`, `FakeSavedDishParserTests` и `MealParserContextTests`. В них проверяются назначение сессии, владельцы, неизменяемость первоисточников, расчёт съеденной порции, конфликт имени и конкурентное подтверждение.

Для исправлений порций начни с `MealEntryWeightTests` и `MealEntryManagementApiTests`: формула и качество нового веса, ID и ревизии, HTTP-условия изменения, исключение удалённых записей и неизменность первоначального подтверждения. Кнопок исправления или восстановления в `wwwroot` пока нет; текущий контракт меняет только массу порции, а не её название, дату или состав.

`ApiResponseCacheTests` проверяет общую политику кэша: успешные ответы, подтверждение и правки дневника, `400` / `404` / `412` / `415` / `428` / `429` / `500` / `503`, сохранение `ETag` и прежнего поведения маршрутов вне `/api`. Фотографии и диапазонные ответы проверяются также в `LabelPhotoOwnershipApiTests`.

`StartupConfigurationApiTests` проверяет ранние ошибки настроек и разделение Development / Production. Его отдельная фабрика использует приватный временный content root, публичные JSON-настройки и ранние `UseSetting`; настоящие User Secrets не подключаются, исходящий HTTP заблокирован и подсчитывается. Фактические пути DbContext и фотографий проверяются дополнительно. Поздний `ConfigureAppConfiguration` не подходит для переопределения настроек, которые читает ранний top-level код: [порядок передачи настроек в DeferredHostBuilder](https://raw.githubusercontent.com/dotnet/aspnetcore/v10.0.11/src/Mvc/Mvc.Testing/src/DeferredHostBuilder.cs).

`ExternalTransportTimeoutTests` проверяет все шесть HTTP-адаптеров: зависшие заголовки / тело, таймаут, отмену вызывающей стороны, заранее отменённый токен, внешний `429`, один вызов и освобождение ответа. `ResponseContentRead` оставляет чтение тела внутри таймаута `HttpClient`; `CancellationToken` передаёт отмену, не подменяя её ошибкой данных.

`ExternalServiceFailureApiTests` проверяет настоящие Groq- / Open Food Facts-адаптеры через шесть маршрутов API в Production. Только транспорт заменён управляемым HTTP-обработчиком, реальная сеть заблокирована. Фабрика задаёт отдельные ранние пути базы / фотографий и временный content root без User Secrets. При отмене тест ждёт завершения всего pipeline, затем сверяет девять таблиц и файлы фото. Внутренний серверный статус отмены `499`, а не `504`, соответствует [обработчику исключений ASP.NET Core](https://raw.githubusercontent.com/dotnet/aspnetcore/v10.0.11/src/Middleware/Diagnostics/src/ExceptionHandler/ExceptionHandlerMiddlewareImpl.cs); клиенту не обещается получение ответа после разрыва соединения. Новых retry-политик или рабочего кода эти проверки не добавляют.

Для диагностики неожиданного HTTP-статуса в тесте используй `ApiTestAssertions.AssertStatusAsync`: он показывает ожидаемый / фактический статус, путь запроса без query string, до 4096 символов ответа, серверные исключения и фактический путь SQLite. Передавай именно фабрику, создавшую клиент, в том числе дочернюю от `WithWebHostBuilder`. Чтение пути не открывает SQLite и не выполняет запросов; при совпадении статуса helper сразу возвращается без чтения тела или доступа к серверу.

`TestApiFactory` регистрирует `TestErrorLogProvider` отдельно в DI каждого сервера. Его потокобезопасная очередь хранит до 128 событий Error / Critical с исключениями, включая stack trace и коды вложенных SQLite-ошибок, но не сохраняет state / scopes и не вызывает formatter журнала. Это только тестовая диагностика: она не добавляет вывод в файлы / консоль и не раскрывает исключения клиентам API. `ApiTestDiagnosticsTests` проверяет девять случаев, включая изоляцию журналов и недоступное тело ответа; `MealWorkflowQueryTests` дополнительно повторяет сценарий на четырёх независимых серверах одновременно. Ограничение размера очереди не является редакцией текста исключений: не используй реальные ключи и личные данные в тестовых входах.

`NutriFlow.Console` — отдельный исполняемый сценарий доменных расчётов. `wwwroot` — временный клиент API, не самостоятельное доменное ядро и не будущий мобильный клиент.

## Резервное копирование

`NutriFlow.Tools/Program.cs` разбирает команды `backup` / `verify` / `restore` и вызывает `Infrastructure.Backups.DataBackup`. Этот исполняемый проект не зависит от `Api`: он не поднимает HTTP, не читает user secrets и не запускает миграции. Ссылка на `Infrastructure` даёт доступ к уже используемому SQLite-провайдеру без нового пакета.

- `Backups/DataBackup.cs` — создание, проверка и восстановление копии, manifest, проверки SQLite и полноты фотографий. `RestoreAsync` проверяет архив до / после копирования, SHA фактических файлов staging и публикует базу / фото только в новое назначение; manifest в runtime-каталог не копируется.
- `Backups/BackupFiles.cs` — безопасные пути, плоский перечень файлов, копирование и SHA-256, очистка только собственных рабочих каталогов.
- `Backups/BackupManifest.cs` — формат метаданных копии.
- `DataBackupTests` — SQLite / WAL, legacy-ссылки, повреждения, пути, отмена и конкуренция без изменения рабочего хранилища.
- `DataRestoreTests` — побайтное восстановление current / legacy, отсутствие перезаписи, повреждённые архивы, пересечения путей, ссылки, предварительная отмена и конкуренция. Все данные искусственные и находятся в собственном временном каталоге.
- `BackupRecoveryApiTests` — восстановление архива через `RestoreAsync` в отдельное хранилище, Production-старт API, миграции, прежние фото, дневник, правки и перезапуск без дублей.

Порядок использования, обязательное условие offline-режима и инструкция пробного запуска — в [BACKUPS.md](BACKUPS.md). Проверяемая база открывается SQLite только после копирования в собственный временный каталог; исходная и готовая копия не получают служебные файлы от проверки. Пробный API также использует отдельную копию, а не файл архива.

## Мобильный клиент

`mobile/NutriFlow.Mobile.slnx` содержит один общий проект .NET MAUI и не связан ProjectReference с сервером. По умолчанию Windows собирает Android, macOS — iOS; платформенные lock-файлы не перезаписывают граф друг друга. Android `MainApplication` вызывает `MauiProgram.CreateMauiApp`. В iOS `Program.Main` запускает `UIApplication.Main` с `AppDelegate`, тот создаёт то же MAUI-приложение. Затем общий `App.CreateWindow` создаёт окно с `MainPage`.

Разметка находится в XAML, C#-часть страницы пока только вызывает `InitializeComponent`. iOS `Info.plist` задаёт платформенные свойства, `PrivacyInfo.xcprivacy` включается ресурсом только в iOS-сборку. Нет HTTP, AI, расчётов, локальной БД или MVVM-пакета. APK заблокирован отсутствующим Android SDK/JDK; iOS C# / XAML и упаковка ARM64-симулятора проверены облачной сборкой. `packages.ios.lock.json` сохранён из её артефакта: 20 пакетов, MAUI 10.0.0 и SDK-инструмент ILLink 10.0.12. Запуск интерфейса, подпись и устройство не проверены. Требования, список загрузок и команды — в [MOBILE_CLIENT.md](MOBILE_CLIENT.md).

`.github/workflows/ios-simulator.yml` отдельно запускает компиляцию и упаковку клиента на облачном Mac по `workflow_dispatch`. Он выбирает Xcode / workload set, выполняет locked restore одного RID и собирает только неподписанный Debug для ARM64-симулятора. Артефакт сборки содержит tar с `.app` и настоящий iOS lock-файл. Повторный run `37648044029` подтвердил восстановление сохранённого графа и сборку; полный текст логов через публичный API недоступен.

`scripts/test-ios-simulator.mjs` — следующий отдельный шаг этого workflow: читает идентификатор из собранного plist, создаёт собственный iPhone для доступного runtime iOS 26.0, выполняет boot / install / launch и сверяет PID приложения через `launchctl` выбранного симулятора. Скриншот между проверками процесса и диагностические файлы сохраняются отдельно, в том числе при обычной ошибке запуска. Команды ограничены по времени; удаляется только собственный UUID. Node.js используется только как CI-инструмент, новые пакеты и зависимости мобильного приложения не добавлены. 32 теста с заменами команд проверяют управление, не настоящий Xcode. Реальный cloud smoke / вид экрана пока не подтверждены; сервер, Apple-аккаунты и IPA для телефона в этот workflow не входят.

## Сборка и публикация

- `NutriFlow.Api.csproj` — `DefaultItemExcludes` исключает личное хранилище, резервные копии, локальные настройки, SQLite-файлы и ключи из автоматических SDK-списков исходников / ресурсов / содержимого. Обычные публичные настройки и интерфейс сохраняются.
- `.dockerignore` — независимо исключает те же приватные категории и `mobile/` из контекста серверного Docker до `COPY`.
- `scripts/Test-Publish.ps1` — настоящая сборка и публикация отслеживаемых публичных исходников в приватной временной копии; 43 искусственных файла, проверки `bin` и publish, DLL, хэшей настроек / интерфейса и сохранности входных файлов. API, миграции и настоящее хранилище не запускаются.
- `.github/workflows/ci.yml` — запускает эту проверку через PowerShell наряду с .NET- и JavaScript-тестами и сборкой Docker.

Исключения действуют на новый пакет, а не очищают ранее созданные каталоги. Это правила путей, не анализ содержимого файлов на секреты. Команды и ограничения описаны в разделе «Пакет приложения» [README](../README.md).
