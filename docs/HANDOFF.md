# NutriFlow: передача проекта разработчику или агенту

Это стартовый документ для продолжения работы без истории чата. Он описывает состояние репозитория, а не разрешает реализовать все перечисленные планы сразу.

## Что мы создаём

NutriFlow — мобильный дневник питания, который реконструирует приготовленное и съеденное из последовательности сообщений, голосовых расшифровок, фотографий этикеток, продуктов и исправлений. Отличие от обычной формы учёта — не чат сам по себе, а связный проверяемый черновик блюда из разрозненной истории.

Приоритет основателя: удобство повседневного использования, затем устойчивый заработок. В перспективе нужна международная аудитория. Веб-клиент не является самостоятельным продуктовым направлением.

## Порядок чтения и источник истины

1. [PRODUCT.md](PRODUCT.md) — замысел и неизменные продуктовые правила.
2. [MVP.md](MVP.md) — границы первой версии, реализованные возможности и критерии приёмки.
3. [ARCHITECTURE.md](ARCHITECTURE.md) — действующая архитектура и отдельно рекомендуемое развитие.
4. [BUSINESS.md](BUSINESS.md) — неутверждённые гипотезы монетизации и порядок их проверки.
5. [FUNDING.md](FUNDING.md) — исследование грантов, источники и ограничения.
6. [ROADMAP.md](ROADMAP.md), актуальная сводка [PROGRESS.md](PROGRESS.md) и [CODE_MAP.md](CODE_MAP.md) — очередность, результаты проверок и конкретные файлы.
7. [ANDROID_INSTALLATION.md](ANDROID_INSTALLATION.md) / [MOBILE_CLIENT.md](MOBILE_CLIENT.md) — запуск и упаковка. [MOBILE_API.md](MOBILE_API.md) описывает отдельный серверный HTTP-вариант, не текущий автономный APK.

Исходники подтверждают фактическую реализацию; PRODUCT фиксирует желаемое поведение. При расхождении нужно назвать пробел, а не объявлять замысел реализованным. PROGRESS содержит исторические неудачные прогоны и прежние гипотезы: они не отменяют более позднюю проверку. Новые решения не считать принятыми только потому, что они перечислены в планах.

## Текущее состояние

- Android `0.2.0`, код версии `2`: нативный .NET MAUI, автономный режим, локальные профили.
- Для каждого GUID профиля — отдельные SQLite, фотографии, настройки и личный Groq-ключ. Профиль не является защищённым облачным аккаунтом.
- Ручные продукты, блюда, дневник, цели, предпросмотр, подтверждение и исправления работают без собственного сервера. AI требует сети и личного ключа.
- Существуют отдельные ASP.NET Core API и временный веб-клиент. APK не обращается к этому API и не переносит его рабочую базу.
- Публичная многопользовательская аутентификация, синхронизация, платежи, подписки, пробные квоты и мобильный экспорт не реализованы.
- Новый функциональный iOS-клиент не прошёл нативную проверку. Исторические успешные iOS-сборки относятся к более раннему статичному экрану.
- Основатель считает UX текущего APK неудовлетворительным. Он не утверждён как целевой дизайн; смена MAUI не согласована.

Подтверждённый baseline: [Android run 37920138556](https://github.com/Vvvv4a40/NutriFlow/actions/runs/37920138556) на `548a8c4` — сборка / подпись / установка / создание профиля / открытие дневника / перезапуск; [CI 37920136563](https://github.com/Vvvv4a40/NutriFlow/actions/runs/37920136563) — полный CI. На этом baseline прошли 992 серверных, 27 мобильных и 462 Node-теста. Это не проверка реального Groq-ключа, камеры / микрофона или конкретного физического телефона. После нового изменения результаты надо получить заново, а не переписывать эти числа как новые.

## Что нельзя потерять при следующем изменении

- AI разбирает структуру; `Domain` детерминированно считает КБЖУ через `decimal`. Память модели не источник пищевой ценности.
- Любая запись съеденного требует предпросмотра и явного подтверждения. Повтор запроса не должен дублировать порции.
- `Diary` и `CreateDish` — разные намерения. Сохранить блюдо не значит его съесть. Сохранённое блюдо не равно редактируемому шаблону `Recipe`.
- Источник и качество данных сохраняются; неизвестные значения не заменяются выдуманными проверенными данными. Не округлять промежуточные вычисления.
- GUID владельца берётся из контекста операции, а не из изменившегося выбора экрана. В будущем сервер определяет владельца из проверенной личности, не доверяет присланному `userId`.
- `Mobile.Core.csproj` компилирует восемь общих исходников workflow / DTO через `Compile Link` из каталога API. Изменения этих файлов проверяются в обоих решениях. Это не зависимость на исполняемый Web-проект.
- Не менять сертификат установленного Android-приложения и не регенерировать потерянный ключ молча. Обновления должны сохранять идентификатор приложения / подпись и не удалять дневник.

## Как проверять

Из корня, без Android SDK:

```powershell
dotnet restore NutriFlow.sln --locked-mode
dotnet build NutriFlow.sln --configuration Release --no-restore --warnaserror
dotnet test NutriFlow.sln --configuration Release --no-build --no-restore
dotnet restore mobile/NutriFlow.Mobile.Core.slnx --locked-mode
dotnet test mobile/NutriFlow.Mobile.Core.slnx --configuration Release --no-restore --warnaserror
node --test scripts/tests/*.test.mjs
```

Для изолированной HTTP-проверки после сборки: `pwsh -File scripts/Test-MealWorkflow.ps1`. Скрипт запускает Fake в отдельном временном хранилище; это не проверка настоящего AI. Обычный `dotnet run --project NutriFlow.Api/NutriFlow.Api.csproj` запускает сконфигурированную установку: переменные окружения / User Secrets могут выбрать реальный Groq и рабочую SQLite. Не использовать этот запуск как безопасную проверку чужой рабочей базы. Android packaging и emulator smoke выполняет ручной workflow `android-apk.yml`; обычные .NET-тесты не заменяют нативную проверку. Команды iOS и ограничения находятся в MOBILE_CLIENT.

## Безопасная передача

Передавать отслеживаемый Git-код и документы, не всю локальную папку без фильтрации. Не передавать `.private/`, `.env*` с секретами, user-secrets, keystore / пароли, рабочие базы, фото, резервные копии, `bin` / `obj`. Git ignore не защищает произвольный ZIP папки. `AGENTS.md` намеренно локальный и игнорируется: необходимые переносимые ограничения изложены здесь, без копирования истории чата.

Не устанавливать SDK / JDK, не принимать лицензии, не включать платные сервисы, не открывать API в интернет и не подавать грантовые заявки без соответствующего разрешения пользователя. Не менять рабочие данные ради проверки. Проверки используют отдельные искусственные хранилища.

Перед правками проверять `git status` и сохранять пользовательские изменения. Имена кода — английские; интерфейс может быть русским. Предпочитать стандартную библиотеку, объяснять назначение каждого нового NuGet-пакета до добавления. Не вводить шаблоны / интерфейсы без конкретной причины, не создавать будущую архитектуру заранее. Комментарии — только о неочевидных причинах, коротко и строчными буквами; без XML-документации / декоративных блоков. После изменения запускать подходящие проверки и фиксировать фактический результат.

## Текущий запрос и следующий шаг

Текущий запрос — документация, объяснение архитектуры и исследование финансирования. Не реализовывать сейчас новый UX, вход, синхронизацию, подписки или лимит «100 токенов».

Следующий предлагаемый продуктовый шаг: разобрать на реальном устройстве один основной сценарий и согласовать мобильный UX-прототип. Затем принять решение о локальном / гибридном режиме и только после этого планировать аккаунты. Вносить небольшие завершённые изменения, объяснять причины, проверять результат и обновлять PROGRESS. Коммиты описывают технический результат без учебных формулировок и номеров этапов; не включать посторонние изменения.
