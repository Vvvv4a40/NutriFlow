# NutriFlow: контракт API для мобильного клиента

Мобильный клиент обращается к ASP.NET Core API напрямую по HTTP. Веб-страница, её JavaScript и браузерное хранилище не участвуют в серверном сценарии. Поиск продуктов, расчёты, вызовы AI и SQLite находятся на сервере; ключ Groq не передаётся в приложение.

Текущая версия использует одного локального владельца без аутентификации клиента. Хранилища разделяют личные данные, включая сохранённые блюда, но это не проверка личности и не готовый публичный сервис. Прежде чем открывать его в интернете, нужны отдельные этапы входа, проверки прав и защищённого развёртывания.

Локальный адрес из профиля запуска: `http://localhost:5198`. На телефоне `localhost` означает сам телефон, а не компьютер с API. Подключение телефона к серверу и HTTPS настраиваются отдельно. OpenAPI доступен в Development по `/openapi/v1.json`.

## Формат данных

- JSON-запросы отправляются с `Content-Type: application/json`; успешные ответы имеют `application/json`.
- Имена JSON-полей — `camelCase`. Статусы и качество данных возвращаются строками с указанным ниже регистром.
- КБЖУ и массы — JSON-числа, не строки. Например, `62.5`, а не `"62,5"`. На сервере расчёты используют `decimal`; клиент не пересчитывает итог вместо сервера.
- `calories` измеряется в ккал, массы и БЖУ — в граммах. Даты передаются в формате `yyyy-MM-dd`, без времени и часового пояса.
- `null` означает отсутствие значения, а не ноль. Не показывайте неизвестное КБЖУ как `0`.
- Промежуточные значения не округляются. Округление для отображения не должно менять данные, отправляемые обратно серверу.

Мобильный клиент всегда явно передаёт `mealDate`, определённую в часовом поясе пользователя. Если поле отсутствует или равно `null`, сервер использует свою локальную дату `DateTime.Today`, которая после развёртывания может отличаться от даты телефона.

`id` — идентификатор сохранённой сессии, UUID. Его нужно сохранить на клиенте, чтобы восстановить сессию после перезапуска приложения.

`previewToken` — непрозрачная строка версии предпросмотра, сейчас 64 шестнадцатеричных символа. Не вычисляйте её на клиенте. Токен меняется при дополнении истории сообщений, даже если числа остались прежними, а также при изменении расчёта или найденных данных продукта. Это не токен авторизации и не секрет: он проверяет, что подтверждается именно просмотренная версия сессии.

## Основные запросы

| Метод и путь | Результат |
| --- | --- |
| `POST /api/meal-sessions` | `201` при создании, `200` при повторе с тем же `Idempotency-Key`; `Location` содержит `/api/meal-sessions/{id}` |
| `GET /api/meal-sessions/{id}` | `200` и текущий `MealSessionResponse`; неизвестная сессия — `404` |
| `POST /api/meal-sessions/{id}/messages` | `200` и обновлённый `MealSessionResponse`; с `Idempotency-Key` повтор не добавляет сообщение ещё раз |
| `POST /api/meal-sessions/{id}/confirm` | `200` или `409` и `ConfirmMealSessionResponse` |
| `GET /api/saved-dishes` | `200` и массив собственных `SavedDishResponse` |
| `GET /api/saved-dishes/{id}` | `200` и сохранённый состав; неизвестное или чужое блюдо — `404` |
| `PUT /api/daily-goals/{date}` | `200` и `DailyProgressResponse` после сохранения цели |
| `GET /api/daily-progress/{date}` | `200` и `DailyProgressResponse` |
| `GET /api/meal-entries/{id}` | `200` и текущая порция с заголовком `ETag`; неизвестная, чужая или удалённая — `404` |
| `PUT /api/meal-entries/{id}` | `200` и исправленная масса / КБЖУ; требует `If-Match` |
| `DELETE /api/meal-entries/{id}` | `204` и исключение порции из дневника; требует `If-Match` |

Создание и дополнение сессии вызывают парсер, но не записывают съеденные порции или собственное блюдо. Только подтверждение сохраняет результат выбранного режима. Сессии, цели, подтверждённые порции и собственные блюда сохраняются в SQLite и восстанавливаются после перезапуска сервера.

### Выбрать намерение сессии

`POST /api/meal-sessions` принимает необязательное строковое поле `purpose`: `Diary` (по умолчанию, также для прежних клиентов) или `CreateDish`. Режим сохраняется в сессии и не меняется при дополнении. Переключение режима на клиенте начинает новую сессию, а не переоформляет старую. `purpose` входит в проверку `Idempotency-Key`: тот же ключ с другим режимом возвращает `409`; прежние ключи `Diary` совместимы.

Для `CreateDish` опишите одно блюдо с названием, ингредиентами и готовым весом. Порция не требуется и не записывается, даже если упомянута в тексте. Массы ингредиентов, продукты и итоговый вес всё равно необходимы для расчёта. `mealDate` сохраняет прежний формат, но создание блюда не меняет дневник этой даты. Подтверждение возвращает пустой `entries` и заполненный `savedDish`.

Для повторного использования выберите `Diary` и отправьте, например, «Съел 150 г моего рагу». Сервер передаёт парсеру только собственные доступные названия; парсер возвращает точное название, а сервер использует сохранённое КБЖУ на 100 г. Произвольная формулировка требует настроенного AI-провайдера. В Fake доступны первые три сообщения примера ниже в `CreateDish`, затем точная фраза `Съел 100 г Демо-блюда.` в `Diary`.

### Создать сессию

```http
POST /api/meal-sessions
Content-Type: application/json
Idempotency-Key: 689ab9e5-cf20-4345-92ad-f899cefb4409

{
  "messages": [
    "Добавил 200 г демо-продукта A.",
    "Потом добавил 100 г демо-продукта B.",
    "Готовое блюдо весит 250 г.",
    "Съел 125 г, потом ещё две порции по 62,5 г."
  ],
  "mealDate": "2026-09-28"
}
```

Это точная поддерживаемая последовательность для `Ai:Provider=Fake` при включённом `Demo:SeedData`. Используйте отдельную демо-базу, если будете подтверждать такой запрос: подтверждение действительно добавит три записи в дневник. Fake не поддерживает произвольные рассказы о еде; свободный текст требует настроенного AI-провайдера.

Мобильный клиент генерирует новый UUID для **одного намерения создать сессию**, сохраняет его до получения ответа и при сетевом повторе отправляет тот же заголовок, те же сообщения в том же порядке и ту же явную `mealDate`. Новый приём пищи требует нового ключа. Это не секрет и не способ входа в аккаунт.

Первый запрос с ключом возвращает `201`; повтор того же исходного запроса — `200` с тем же `id` и текущим сохранённым состоянием сессии. Даже если после создания в сессию уже добавили сообщения, исходный запрос с прежним ключом возвращает её текущую версию. Ключ с другими сообщениями или датой возвращает `409` ProblemDetails, не меняя сессию. Пустой, неверно записанный UUID или отсутствие явной `mealDate` с ключом возвращают `400`. Без заголовка остаётся старое поведение: каждый успешный `POST` создаёт новую сессию.

Ключ и отпечаток исходного запроса сохраняются в SQLite, поэтому повтор работает после перезапуска сервера. При строго одновременной отправке двух первых запросов AI может быть вызван дважды, но уникальность ключа в пределах внутреннего владельца допускает только одну сессию. Сейчас API всегда использует одного локального владельца; это не проверка личности клиента.

Ограничения истории: от 1 до 50 сообщений, каждое непустое и не длиннее 4000 символов, суммарно не больше 20000 символов. Дополнение сессии проверяется с учётом всей накопленной истории.

### Дополнить и восстановить сессию

```http
POST /api/meal-sessions/{id}/messages
Content-Type: application/json
Idempotency-Key: 6f7ab823-c5ac-45d9-aa64-8d7356a92f61

{
  "message": "В сухом виде."
}
```

Для каждого **нового дополнения** мобильный клиент создаёт новый UUID и сохраняет его до получения ответа. При сетевом повторе отправьте тот же ключ и точно тот же текст: API вернёт `200` с текущей версией сессии без повторного добавления и AI-разбора, даже если после первого запроса появились другие сообщения или сессия была подтверждена. Тот же ключ с другим текстом в этой сессии даёт `409` ProblemDetails. Тот же текст с **новым** ключом считается новым сообщением. Ключ действует только внутри указанной сессии; он не является авторизацией.

Без заголовка остаётся прежнее поведение: каждый успешный запрос добавляет сообщение. Повреждённый, пустой или повторённый заголовок даёт `400`. Строго одновременные первые запросы с одним ключом могут оба успеть вызвать AI, но только одно сообщение сохранится: ключ записывается вместе с историей в одном условном обновлении SQLite.

В Fake это уточнение поддерживается для сессии из трёх сообщений: «Добавил 500 г макарон.», «Готовое блюдо весит 900 г.», «Съел 300 г.». После уточнения продуктом становится «Макароны сухие»; без такого продукта в каталоге сессия остаётся `NeedsProducts`.

`GET /api/meal-sessions/{id}` возвращает сохранённую историю и предпросмотр. Для неподтверждённой сессии сервер проверяет актуальные продукты каталога: статус и токен могут измениться без нового сообщения. Подтверждённый предпросмотр сохраняется как снимок и не пересчитывается при последующем изменении продуктов.

В подтверждённую сессию нельзя добавить **новое** сообщение: сервер вернёт `409`. Повтор уже успешно добавленного сообщения с прежним `Idempotency-Key` вернёт текущую подтверждённую сессию с `200`. Конкурентное изменение истории с другим ключом также может вернуть `409`; клиент должен загрузить текущую сессию перед дальнейшими действиями.

## Сессия и предпросмотр

`MealSessionResponse` содержит следующие поля:

| Поле | Тип и смысл |
| --- | --- |
| `id` | UUID сессии |
| `status` | Состояние из таблицы ниже |
| `purpose` | `Diary` или `CreateDish`; отсутствующее поле в прежнем ответе трактуется как `Diary` |
| `mealDate` | Дата дневника `yyyy-MM-dd` |
| `messages` | Упорядоченный массив строк |
| `previewToken` | Текущая версия предпросмотра |
| `canConfirm` | Разрешено ли сейчас подтверждение |
| `clarificationQuestions` | Массив вопросов парсера, может быть пустым |
| `issues` | Массив препятствий для расчёта или подтверждения |
| `dishes` | Массив отдельных блюд с ингредиентами и порциями |

| `status` | Действие клиента |
| --- | --- |
| `NeedsClarification` | Показать вопросы и недостающие массы или порции; принять уточнение |
| `NeedsProducts` | Показать нерешённые продукты; после пополнения каталога загрузить сессию снова |
| `ReadyForConfirmation` | Показать рассчитанные значения и запросить явное подтверждение пользователя |
| `Confirmed` | Показать сохранённый результат; сессия больше не редактируется |

Ориентируйтесь на серверные `status` и `canConfirm`, а не на наличие отдельных чисел: сервер может рассчитать КБЖУ ингредиентов, пока вес готового блюда или порция ещё неизвестны.

Вложенные объекты имеют такой состав:

- `issues[]`: `code`, `dishName`, `ingredientName` (строка или `null`), `message`. Коды: `product_not_found`, `product_ambiguous`, `ingredient_weight_missing`, `removed_weight_missing`, `final_weight_missing`, `portion_missing`, `single_dish_required`, `saved_dish_invalid`. Последние два блокируют сохранение нескольких блюд или недопустимого названия / КБЖУ; `portion_missing` относится только к `Diary`.
- `dishes[]`: `name`, `finalWeightInGrams`, `finalWeightQuality`, `totalNutrition`, `totalNutritionQuality`, `nutritionPer100Grams`, `nutritionPer100GramsQuality`, `ingredients`, `portions`. Неизвестные масса, КБЖУ и качество вычисленного значения могут быть `null`.
- `ingredients[]`: `productName`, `weightInGrams`, `weightQuality`, `removedWeightInGrams`, `removedWeightQuality`, `includedWeightInGrams`, `resolvedProduct`, `nutrition`. Неизвестные массы, ненайденный продукт и невычисленное КБЖУ могут быть `null`.
- `resolvedProduct`: `name`, `calories`, `proteinGrams`, `fatGrams`, `carbohydratesGrams`, `sourceKind`, `dataQuality`, `sourceName`, `sourceReference`, `barcode`. Последние два поля могут быть `null`. КБЖУ продукта указано на 100 г.
- `portions[]`: `weightInGrams`, `fractionOfDish`, `weightQuality`, `nutrition`, `nutritionQuality`. Порция может быть задана массой или долей; у доли `0.5` смысл «половина готового блюда». Если итоговый вес известен, сервер также вычисляет её массу. Неизвестные и неприменимые значения возвращаются как `null`.

Каждый объект КБЖУ (`NutritionResponse`) имеет одинаковую форму:

```json
{
  "calories": 200,
  "proteinGrams": 12.5,
  "fatGrams": 10,
  "carbohydratesGrams": 15
}
```

Для `totalNutrition` это всё блюдо, для `nutritionPer100Grams` — 100 г готового блюда, для `ingredients[].nutrition` — вошедшая в блюдо масса ингредиента, для `portions[].nutrition` — съеденная порция.

Значения качества: `Unknown`, `Exact`, `Verified`, `Estimated`. Это категории происхождения и точности, не проценты уверенности модели. Итог наследует худшее качество составляющих. Показывайте приблизительность пользователю. В демо-каталоге качество `Unknown`: демонстрационные данные не выдаются за проверенные пищевые значения.

`sourceKind` продукта может быть `Unknown`, `NutriFlowCatalog`, `ManualInput`, `LabelPhoto`, `ExternalService`, `WebPage`, `DishPhoto`, `SavedDish`. `sourceName` и `sourceReference` описывают происхождение данных; ссылки и фотографии должны оставаться доступными для проверки пользователем. Для собственного блюда ссылка имеет вид `saved-dish:<UUID без дефисов>`; состав и исходные источники доступны через `GET /api/saved-dishes/{id}`.

## Подтверждение

```http
POST /api/meal-sessions/{id}/confirm
Content-Type: application/json

{
  "previewToken": "<токен из последнего просмотренного ответа>"
}
```

Успешное подтверждение атомарно меняет статус сессии и сохраняет все рассчитанные порции (`Diary`) либо одно собственное блюдо (`CreateDish`): частичного добавления результата не происходит.

Ответ `ConfirmMealSessionResponse`:

| Поле | Смысл |
| --- | --- |
| `outcome` | `Confirmed`, `AlreadyConfirmed`, `StalePreview` или `NotReady` |
| `message` | Пояснение конфликта либо `null` |
| `session` | Полный актуальный `MealSessionResponse` |
| `entries` | Массив текущих съеденных порций: `id`, `revision`, `name`, `weightInGrams`, `nutrition`, `quality` |
| `savedDish` | `null` для дневника и неуспешного подтверждения; сохранённое блюдо для успешного `CreateDish` |

`200 / Confirmed` означает первую успешную запись. Повтор того же запроса с теми же `id` и `previewToken` возвращает `200 / AlreadyConfirmed` и уже сохранённые порции, не создавая дубликаты. Это работает и после перезапуска сервера.

После исправления или удаления порции повтор подтверждения возвращает текущие активные `entries`, а не восстанавливает исходные массы или удалённые записи. `session.dishes` при этом остаётся историческим снимком первоначально подтверждённого предпросмотра. Для текущего дневного баланса используйте дневник, не сумму исторических порций из сессии.

`409 / StalePreview` означает устаревшую версию. Покажите `session` из ответа и получите новое подтверждение пользователя; автоматически отправлять новый токен нельзя. `409 / NotReady` означает неразрешённые вопросы или проблемы продуктов. При обоих конфликтах `entries` пуст и этот запрос не записывает новые порции.

В `CreateDish` повтор подтверждения также возвращает `200 / AlreadyConfirmed` с тем же `savedDish.id`, без второй записи. Конфликт собственного имени возвращает `409` ProblemDetails: попросите другое название и добавьте уточнение в ту же неподтверждённую сессию. Прежнее блюдо не перезаписывается. Если КБЖУ одноимённого продукта и собственного блюда различаются, предпросмотр получает `product_ambiguous`.

### Читать сохранённые блюда

`SavedDishResponse` содержит `id`, `name`, `sourceSessionId`, `finalWeightInGrams`, `nutritionPer100Grams` (обычный `NutritionResponse`) и `nutritionQuality`. `GET /api/saved-dishes` возвращает массив этих объектов; `GET /api/saved-dishes/{id}` — объект с полями `savedDish` и `dish` (сохранённый `DishPreviewResponse` с ингредиентами и их источниками).

Это неизменяемый снимок подтверждённого состава и КБЖУ, не шаблон рецепта и не складской остаток. Изменение каталога не пересчитывает сохранённое блюдо. Его качество не становится `Exact` только из-за сохранения: наследуется худшая категория исходных данных. Имя уникально у владельца после нормализации регистра, Unicode и крайних пробелов; в HTTP-контракте пока нет изменения или удаления собственного блюда.

## Дневная цель и прогресс

```http
PUT /api/daily-goals/2026-09-28
Content-Type: application/json

{
  "calories": 2000,
  "proteinGrams": 100,
  "fatGrams": 70,
  "carbohydratesGrams": 250
}
```

Все четыре значения цели неотрицательные. PUT создаёт или заменяет цель указанной даты; повтор одинакового PUT не создаёт дополнительных целей.

Ответ PUT и ответ `GET /api/daily-progress/2026-09-28` имеют одинаковую форму:

| Поле | Тип и смысл |
| --- | --- |
| `date` | Запрошенная дата |
| `goal` | `NutritionResponse` или `null`, если цель не задана |
| `consumed` | Сумма КБЖУ подтверждённых порций; нули для пустого дня |
| `remaining` | Остаток до цели по каждому показателю, минимум ноль; `null` без цели |
| `exceeded` | Превышение цели по каждому показателю, минимум ноль; `null` без цели |
| `entries` | Текущие съеденные порции с `id`, `revision`, `name`, `weightInGrams`, `nutrition`, `quality`; пустой массив для пустого дня |

Даты независимы: записи и цель одного дня не попадают в другой. `id` порции — положительное целое число из SQLite, не UUID и не способ авторизации. `revision` — неотрицательная версия: `0` у исходной записи, затем увеличивается при успешной коррекции или первом удалении. Эти поля добавлены к прежнему ответу; старые клиенты могут их игнорировать.

Ожидаемые числа для точной Fake-последовательности выше:

| Результат | Масса, г | Ккал | Белки, г | Жиры, г | Углеводы, г |
| --- | ---: | ---: | ---: | ---: | ---: |
| Всё блюдо | 250 | 400 | 25 | 20 | 30 |
| На 100 г готового блюда | 100 | 160 | 10 | 8 | 12 |
| Первая порция | 125 | 200 | 12.5 | 10 | 15 |
| Вторая порция | 62.5 | 100 | 6.25 | 5 | 7.5 |
| Третья порция | 62.5 | 100 | 6.25 | 5 | 7.5 |

До подтверждения дневник пуст. После подтверждения в нём три записи с качеством `Unknown`; `consumed` равен 400 ккал / 25 Б / 20 Ж / 30 У. Для цели из примера `remaining` равен 1600 ккал / 75 Б / 50 Ж / 220 У, `exceeded` — нули. Повтор подтверждения оставляет три записи и те же суммы.

## Исправить или убрать порцию

Масса исправляется для того же съеденного продукта или блюда. Название, дата, состав и исходная пищевая ценность не меняются; при ошибке в самом продукте уберите запись и создайте новую сессию.

Сначала возьмите `id` и `revision` из дневного прогресса или ответа подтверждения. `GET /api/meal-entries/{id}` возвращает тот же `MealEntryResponse` и сильный ETag, например `"0"`. GET и успешный PUT используют `Cache-Control: private, no-store`.

```http
PUT /api/meal-entries/42
Content-Type: application/json
If-Match: "0"

{
  "weightInGrams": 100,
  "weightQuality": "Exact"
}
```

`weightInGrams` обязателен и положителен. `weightQuality` — `Exact` (по умолчанию) или `Estimated`; неизвестная масса и заявление о проверенном источнике не являются допустимой коррекцией веса. Успех — `200` с обновлённой порцией, `revision: 1` и `ETag: "1"`. Повторные исправления всегда считаются C#-кодом из исходного подтверждённого снимка, а не из предыдущего исправления; каталог и AI не вызываются. Качество не улучшается автоматически относительно исходного снимка, а приблизительная новая масса может его снизить.

```http
DELETE /api/meal-entries/42
If-Match: "1"
```

Успех — `204` без тела. Порция исключается из дневного прогресса и результатов повторного подтверждения; исходная запись и подтверждённый предпросмотр остаются в SQLite. Повтор удаления собственной уже удалённой записи с корректно оформленным `If-Match` также возвращает `204`, не меняя версию. GET и PUT удалённой записи возвращают `404`. Восстановления через API пока нет.

У активной записи устаревший `If-Match` возвращает `412` ProblemDetails без изменения данных. Загрузите текущую порцию и получите новое решение пользователя; нельзя молча повторять команду с новой версией. При потерянном ответе PUT сначала прочитайте запись: старый ETag может уже устареть, даже если первая команда успешно выполнена. При потерянном ответе DELETE допустим повтор прежней команды.

Отсутствующий `If-Match` — `428`. Принимается ровно одна каноническая строка вида `"0"` или `"12"`, неотрицательная версия в диапазоне `int`. Пустой, слабый (`W/"0"`), непроцитированный, составной или `*` ETag, отрицательное число и ведущие нули дают `400`. Неверная масса / качество и арифметическое переполнение предлагаемой коррекции также дают `400` до записи; повреждённые сохранённые данные являются серверной ошибкой `500`, а не неверным вводом клиента.

## Ошибки и повторы запросов

Обычные ошибки имеют `Content-Type: application/problem+json` и поля `status`, `title`, необязательное `detail`. Ошибки прикладной валидации дополнительно содержат `errors`: словарь массивов строк. Например, значимые поля ответа на пустую историю:

```json
{
  "status": 400,
  "title": "One or more validation errors occurred.",
  "errors": {
    "Messages": ["At least one captured message is required."]
  }
}
```

Ключ истории сейчас именно `Messages` с заглавной буквы, хотя входное JSON-поле — `messages`. Для токена используется `previewToken`, для цели — `goal`. Ошибки связывания JSON или неверной даты могут не иметь словаря `errors`; клиент должен уметь показать общее сообщение по `status` и `title`.

Особый случай: `409 / StalePreview` и `409 / NotReady` от `/confirm` — **не ProblemDetails**, а `application/json` с `outcome`, `message`, `session`, `entries`, `savedDish`. Конфликт имени при сохранении блюда и `409` от добавления сообщения, напротив, являются ProblemDetails. Не пытайтесь разобрать все ответы одинаково. Для путей `/api` пустые ошибки HTTP дополняются ProblemDetails, в том числе неверный UUID (`404`), повреждённый JSON (`400`) и неподходящий Content-Type (`415`) в Production. Клиенту всё равно нужен запасной обработчик пустого или не-JSON ответа: его может вернуть прокси или недоступный сервер.

| Код | Реакция клиента |
| --- | --- |
| `400` | Исправить JSON, дату или значения; не повторять без изменения запроса |
| `404` | Сессия или маршрут не найдены; проверить сохранённый `id` и адрес |
| `409` | Обновить сессию и показать конфликт; для подтверждения обработать `outcome` |
| `412` | Версия порции устарела: прочитать текущую запись и предложить пользователю проверить изменение |
| `415` | Отправить тело в ожидаемом формате и с правильным Content-Type |
| `422` | Ввод не поддержан парсером; для аудио также возможна нераспознанная речь |
| `429` | Подождать; учитывать `Retry-After`, если заголовок присутствует |
| `428` | Передать версию исправляемой / удаляемой порции в `If-Match` |
| `500` | Внутренняя ошибка сервера, в том числе повреждённые сохранённые данные; не запускать бесконечный повтор |
| `502` | Ошибка или некорректный ответ внешнего провайдера |
| `503` | Возможность не настроена, например распознавание голоса в Fake |
| `504` | Внешний провайдер не ответил за отведённое время |

Неверный ответ парсера и повреждённая запись SQLite — разные ошибки. Для создания и дополнения сессии `502` о неверном черновике относится только к вызову парсера; повреждение сохранённых сообщений, черновика или ключей повторов возвращает `500`. Вложенные данные сохранённого предпросмотра также проверяются перед выдачей подтверждённой сессии, повторного подтверждения или ответа с устаревшим токеном: некорректный снимок возвращает `500`, не меняя дневник. В Production такой ответ не раскрывает содержимое записи или внутреннее исключение.

Повторы после обрыва связи:

- GET можно повторять. GET сессии может обновить ещё не подтверждённый предпросмотр; новый токен и числа нужно показать пользователю.
- PUT цели можно повторить с той же датой и тем же телом. Это замена значения, а не добавление записи.
- Подтверждение можно повторить с теми же `id` и просмотренным `previewToken`. Нельзя подменять токен свежим без просмотра пользователем.
- POST создания сессии можно безопасно повторить с тем же `Idempotency-Key`, исходными сообщениями и явной датой. После потери ответа повтор вернёт прежний `id`; не генерируйте новый ключ для повтора. Без ключа повтор по-прежнему создаёт новую сессию.
- POST дополнения можно повторить с тем же `Idempotency-Key` и текстом. Без ключа повтор может добавить сообщение второй раз; после неопределённого сетевого результата сначала загрузите сессию и проверьте историю.

Ограничитель внешних операций общий для адреса клиента: до 12 запросов в минуту на создание/дополнение/разбор сессий, внешние продукты, аудио и этикетки. Мобильный клиент не должен запускать эти операции в непрерывном цикле повторов.

## Личный и общий каталог

Формат продуктовых запросов не меняется: клиент не передаёт `userId` или признак публикации. Ручное сохранение и продукт из этикетки относятся к владельцу, которого выбирает сервер; сейчас это один локальный пользователь без проверки личности.

Поиск по штрихкоду сначала выбирает личную запись, затем общий кэш, затем Open Food Facts. Новый проверенный по формату ответ внешней базы сохраняется в общий кэш с исходным качеством, а не становится автоматически `Verified`. Старый каталог мигрирует в личный, независимо от происхождения записей.

Алиас личный даже у общего продукта. При наличии личной версии того же штрихкода поиск по имени и собственному алиасу общей записи возвращает личную версию без дубля. Продукты с одинаковым именем, но разными штрихкодами, остаются разными кандидатами. Чужие личные записи не участвуют в поиске или улучшении данных.

Это проверено на уровне хранилищ с двумя владельцами, но не означает готовую многопользовательскую защиту HTTP. Фотографии также ограничены серверным владельцем; проверки личности клиента пока нет.

## Голос и фотографии

`GET /api/capabilities` возвращает `aiProvider`, `supportsFreeText`, `supportsLabelPhotos`, `supportsSpeechTranscription`. Используйте эти флаги, не названия провайдеров, для доступности функций клиента.

- `POST /api/audio/transcribe`: `multipart/form-data`, файловое поле `audio`, до 8 MiB; WAV, MP3, WebM, M4A, Ogg. Ответ `200` — `{"text":"распознанная речь"}`. Аудио не сохраняется постоянно; текст не создаёт сессию и не попадает в дневник автоматически. После пользовательской проверки отправьте текст обычным сообщением.
- `POST /api/labels/analyze`: `multipart/form-data`, файловое поле `photo`, до 8 MiB; JPEG, PNG, WebP. Ответ содержит `photoReference`, `productName`, `basis`, четыре nullable-поля КБЖУ, `clarificationQuestions`, `canCreateProduct`. Фотография сохраняется, но продукт ещё не создаётся.
- `POST /api/products/from-label`: JSON с проверенными пользователем `photoReference`, `basis: "Per100Grams"`, `name`, `calories`, `proteinGrams`, `fatGrams`, `carbohydratesGrams` и необязательным `barcode`. Непересчитанные значения на порцию или на 100 мл сохранять этим запросом нельзя.
- `GET /api/label-photos/{fileName}`: исходное изображение с прежним MIME, только при наличии файла и записи текущего серверного владельца. Чужие и неизвестные ссылки одинаково возвращают `404` ProblemDetails; ответы имеют `Cache-Control: private, no-store`. Владелец не передаётся в URL, JSON или заголовке.

`photoReference` сохраняет формат `label-photo:<fileName>` и должен храниться как непрозрачная ссылка. Создание продукта с чужой, незарегистрированной или отсутствующей фотографией возвращает `400` без записи продукта. Анализ фотографии ещё не подтверждает её КБЖУ и не делает продукт общим. При обновлении старой установки снимки однократно относятся к локальному владельцу; ссылки и содержимое не меняются. Правила переноса и резервных копий — в [USER_DATA.md](USER_DATA.md).

Для multipart клиентская HTTP-библиотека сама задаёт `Content-Type` с boundary. Ограничение записи в 60 секунд относится к нынешнему веб-клиенту; серверный контракт аудио ограничивает размер файла, а не длительность записи. Мобильный клиент должен управлять микрофоном и камерой самостоятельно, не заимствуя браузерные модули.

Механизм формирования ProblemDetails использует стандартные средства ASP.NET Core: [AddProblemDetails и UseStatusCodePages](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling-api?view=aspnetcore-10.0).
