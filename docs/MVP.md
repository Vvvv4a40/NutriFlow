# MVP и границы первой версии

MVP — minimum viable product: минимальная версия, на которой проверяется основная пользовательская ценность. В запросе использовано «MVD»; здесь выбран стандартный термин MVP. Готовый APK, продуктовый MVP и публичный коммерческий релиз — разные уровни готовности.

## Для кого и какую задачу решаем

Первичная аудитория — человек, который готовит дома и хочет учитывать питание, но не хочет каждый раз вручную раскладывать историю готовки по полям. Это гипотеза аудитории, не результат исследования рынка. NutriFlow не позиционируется как диагностика, лечение или назначение лечебного питания.

Основная проверяемая ценность: пользователь естественно рассказывает о готовке и съеденном, получает понятный проверяемый состав и быстрее делает корректную запись, сохраняя возможность исправить неизвестное.

## Целевой сквозной сценарий

Это продуктовый сценарий, а не утверждение о готовности всех способов ввода. Сейчас фото этикетки отдельно создаёт проверяемый продукт каталога, не прикрепляется как полноценное медиасобытие к реконструкции сессии.

1. Создать или выбрать профиль.
2. Выбрать намерение: создать собственное блюдо либо записать съеденное.
3. Добавить несколько сообщений, фото этикетки или проверенную голосовую расшифровку.
4. Получить объединённый черновик: ингредиенты, массы / качество, готовый вес, съеденная порция, источники и существенные вопросы.
5. Исправить состав / неизвестный продукт и увидеть детерминированный расчёт.
6. Явно подтвердить результат: `CreateDish` сохраняет блюдо, `Diary` — съеденное.
7. Позже добавить порцию собственного блюда естественной фразой либо выбором, не вводя заново весь состав.
8. Увидеть дневной прогресс, исправить ошибочную массу или убрать запись.

Пример истории: «Добавил примерно 600 г говядины» → «пачку овощной смеси» + её этикетка → «20 г масла» → «готовое блюдо 1180 г» → «съел 350 г». Неизвестные КБЖУ / масса пачки не берутся из памяти модели. Если надёжных данных ещё нет, черновик требует разрешения пробела; название блюда не делает состав проверенным.

## Что есть и чего ещё нет

| Область | Состояние |
| --- | --- |
| Локальные профили и разделение SQLite / фото | Реализовано и покрыто Core-тестами; это не login |
| Личный ключ по GUID профиля | Реализован через MAUI SecureStorage; нативная приёмка ключа ещё нужна, Core-тесты не проверяют SecureStorage |
| Ручные продукты / блюда / порции, цели, изменения | Реализовано, офлайн |
| Естественный текст / фото этикетки / речь | Интеграции реализованы; в новом APK реальный ключ и устройство ещё требуют приёмки |
| Сохранение блюда отдельно от дневника, повторное использование | Реализовано; хранится снимок состава, не полный редактор рецептов |
| Источники, качество, local-first штрихкод | Реализовано; внешняя база не становится Verified автоматически |
| Android APK, постоянная подпись, native startup / restart | Подтверждено облачным Android 35 / x64 |
| Удобство APK для ежедневного использования | Основатель сообщил о неудовлетворительном UX; требуется отдельная работа |
| Перенос данных / Google / Apple / email / пароль | Не реализовано |
| Мобильный backup / экспорт | Не реализовано; удаление приложения уничтожает локальные данные |
| Подписки, платежи и бесплатный лимит AI | Только план |
| Функциональный iOS после автономной переделки | Не проверен нативно |

## Что не включено в текущий MVP

Медицинские рекомендации, автоматическое меню / планирование будущего питания, социальная сеть, учёт оставшегося запаса кастрюли, полноценные изменяемые Recipe, точное определение КБЖУ тарелки по одному фото, автоматическая синхронизация и авторизация, магазинные подписки. Эти идеи нельзя выдавать за действующие возможности.

Фотография готовой еды в перспективе допустима только как явно приблизительная оценка. В текущем сценарии распознавание этикетки и оценка готовой тарелки не взаимозаменяемы.

## Критерии приёмки локальной версии

- Два профиля не смешивают продукты, сессии, блюда, дневник, цели, фото и ключи.
- Без сети ручной сценарий доступен; отсутствие ключа не заменяется Fake-разбором произвольного текста.
- Без подтверждения порция не попадает в дневник; повтор подтверждения не дублирует её.
- `CreateDish` не изменяет дневной итог; последующая съеденная порция изменяет его ровно один раз.
- Готовый вес влияет на значение на 100 г, но сам по себе не уничтожает питательные вещества ингредиентов.
- Источник / приближённость видимы до подтверждения; исправление массы не делает исходные приблизительные данные точными.
- После перезапуска записи и последняя сохранённая незавершённая сессия доступны; набранный, но ещё не отправленный текст сейчас хранится только в памяти и не является сохранённой сессией.
- Обновление APK той же подписью сохраняет данные; приёмка физического устройства отдельно подтверждает это.
- Реальные текст, фото / разрешения, аудио / расшифровка проверены с личным ключом; ошибки сети не теряют ввод и не создают ложную запись.

## Критерии будущей публичной версии

До массового распространения нужны согласованный UX и приёмка на физических устройствах, понятное сохранение / восстановление данных, приватность и согласие на отправку медиа AI. Если обещаны аккаунты — настоящий вход, права на каждую запись / фото и проверенный перенос между двумя устройствами. Если обещана подписка — серверная проверка права / квот, контролируемая себестоимость и корректные платежные сценарии. Эти условия не объявляются выполненными текущим APK.

## Следующий ограниченный шаг

Сначала проверить основной сценарий и согласовать UX-прототип: какие экраны нужны, где пользователю приходится думать, сколько обязательных действий, как он видит исправления / источник и продолжает начатое. Пока не назначены цена, лимит токенов, провайдер входа или новая UI-технология.
