# NutriFlow: концепт продукта

NutriFlow — приложение для подсчёта калорий, белков, жиров и углеводов. Оно превращает последовательность разрозненных сообщений, фотографий и уточнений пользователя в структурированную модель приготовленного и съеденного.

## Целевая платформа

Главный результат — удобное мобильное приложение для личного учёта питания. Текущий Android-клиент на .NET MAUI самостоятельно хранит данные, вызывает интеграции и использует общее C#-ядро расчётов; собственный сервер ему не нужен. ASP.NET Core API сохранён как независимый серверный вариант и возможная основа будущих облачных функций. Веб-интерфейс — временный инструмент проверки API, не приоритетный продукт.

Сначала важны удобство основателя и реальных пользователей, затем устойчивый заработок. Международный рынок — намерение на перспективу, не уже подтверждённая готовность к запуску. [Границы текущего MVP](MVP.md), [архитектура](ARCHITECTURE.md) и [бизнес-гипотезы](BUSINESS.md) отделяют реализованное от будущих решений.

## Основной сценарий

Пользователь постепенно описывает готовку: добавляет продукты, массы, фотографии этикеток, итоговый вес блюда и размер съеденной порции. Система объединяет эти события, находит пищевую ценность ингредиентов, формирует черновик блюда и задаёт только действительно необходимые вопросы. Запись в дневной рацион создаётся после подтверждения пользователя.

Одна сессия может описывать несколько отдельных продуктов или блюд одного приёма пищи.

Ключевая ценность — реконструкция связной истории из нескольких вводов, а не только калькулятор или единичный запрос к модели. Например: «около 600 г говядины» → «пачка овощей» → фото этикетки → «20 г масла» → «готовое блюдо 1180 г» → «съел 350 г». История должна оставаться исправляемой до подтверждения, без принуждения пользователя к порядку полей.

Это полный продуктовый замысел. Сейчас текст объединяется в сессии, речь сначала превращается в проверяемый текст, а фото этикетки отдельно распознаётся и сохраняется в каталог после проверки. Универсальное объединение произвольных медиа и рецептов внутри одной сессии ещё не реализовано.

## Два намерения ввода

Над черновиком пользователь выбирает «Внести в дневник» или «Создать блюдо». Намерение сессии (`MealSessionPurpose`) не является её состоянием: в обоих режимах черновик проходит проверку и подтверждение, но результат сохранения различается.

- `Diary` — фактически съеденные продукты и порции, включая собственные ранее сохранённые блюда. Одна сессия может содержать несколько элементов приёма пищи. «Дневной план» в текущей версии означает дневник съеденного, не планирование будущего питания.
- `CreateDish` — одно собственное блюдо с названием, составом и итоговым готовым весом. Размер съеденной порции не требуется; подтверждение не создаёт записей дневника.

Сохранённое блюдо хранит снимок рассчитанных КБЖУ, качества и состава со ссылками на источники. Последующие изменения каталога не меняют его исторический результат. При фразе «Съел 150 г моего рагу» AI выбирает каноническое название из собственных сохранённых блюд, а C#-ядро рассчитывает порцию из сохранённого значения на 100 г. AI не восстанавливает состав из памяти и не придумывает пищевую ценность.

Это повторное использование конкретного приготовленного состава, а не реализация `Recipe` как изменяемого шаблона рецепта. Остатки блюда не списываются автоматически. Одинаковые имена собственных блюд не перезаписываются; значимое различие между одноимённым продуктом и блюдом требует разрешения неоднозначности.

## Граница ответственности AI

В целевом продукте AI отвечает за:

- объединять сообщения и фотографии;
- извлекать продукты, массы и связи между ними;
- находить существенные неоднозначности;
- формировать структурированный черновик и вопросы.

AI не выполняет итоговую арифметику. Расчёты КБЖУ выполняются детерминированным C#-кодом и проверяются тестами.

Ошибка / недоступность AI не разрешает незаметно заменить результат выдуманными данными. Пользователь должен видеть ограничение и иметь возможность ручного ввода.

## Источники пищевой ценности

Целевой автоматический порядок поиска:

1. собственная база NutriFlow;
2. ранее найденные и сохранённые продукты;
3. внешние продуктовые базы, API или веб-источники;
4. приблизительная оценка, если надёжных данных нет.

Пользователь не выбирает источник поиска. Внешние данные нужно проверить на пригодность, привести к единой базе измерения и сохранить с происхождением; ответ AI сам по себе не является проверенным источником. Приблизительная оценка допустима только явно обозначенной, а не под видом найденных фактов.

Реализовано сейчас: локальный каталог и внешний поиск по штрихкоду через Open Food Facts с валидацией и кэшированием. Успешный импорт получает качество `Unknown`, а не автоматически `Verified`. Универсальный веб-поиск по названию и автоматическая оценка при отсутствии данных ещё не реализованы; нехватка пищевых данных требует заполнения продукта.

## Качество и происхождение

Качество отвечает на вопрос «насколько точным считаем значение», источник — «откуда его получили». Их нельзя заменять одним числом уверенности AI. Продуктовый язык должен различать точный ручной ввод, проверенную базу, этикетку, приблизительную массу пользователя, визуальную оценку и неизвестные данные.

В текущем коде `DataQuality` содержит `Unknown`, `Exact`, `Verified`, `Estimated`; `NutritionSourceKind` различает `Unknown`, `NutriFlowCatalog`, `ManualInput`, `LabelPhoto`, `ExternalService`, `WebPage`, `DishPhoto`, `SavedDish`. Это не обещание реализации каждого способа получения данных: например, готовую тарелку приложение пока не распознаёт. Числовые значения enum не задают порядок качества; правило ухудшения реализуется отдельно.

Для продукта сохраняются источник / ссылка / фото, а для массы — своё качество. Сканирование этикетки не делает её безошибочной: распознанное нужно проверить. Фото готового блюда в будущем может давать только явно приблизительный результат. Проценты уверенности модели не используются как доказательство точности.

## Уточнения

Вопрос нужен, только если одновременно:

1. Есть минимум две разумные трактовки.
2. Разница заметно влияет на результат.
3. Ответа нет в остальных сообщениях, фото или базе.
4. Предположение может серьёзно исказить расчёт.

Пример: «500 г макарон — сухих или сваренных?» По умолчанию:

- «примерно 600 г» уже означает приблизительную массу, повторный вопрос не нужен;
- указанные 20 г масла полностью входят в блюдо, если пользователь не сообщил об удалении;
- другие продукты также входят полностью, пока явно не указаны потери;
- несущественные специи не требуют уточнений;
- приложение само выбирает путь поиска пищевых данных.

Существенные вопросы желательно собирать в один компактный набор к завершению ввода. Если пользователь не знает ответа, целевой UX должен позволять явно принять приблизительную оценку; нельзя молча объявлять её точной. Это правило не означает, что все будущие виды оценки уже реализованы.

## Основные понятия

- `CaptureSession` — временная сессия ввода и уточнений.
- `InputEvent` — одно сообщение, фотография или другое событие сессии.
- `Product` — продукт и его пищевая ценность с источником.
- `Recipe` — повторно используемый шаблон блюда.
- `DishBatch` — конкретно приготовленная партия блюда.
- `MealEntry` — фактически съеденная порция.
- `DailyGoal` — дневная цель по КБЖУ.
- `NutritionSource` — происхождение пищевых данных.
- `DataQuality` — понятная категория точности данных.

Рецепт, приготовленная партия и съеденная порция — разные сущности. Этот список содержит и концептуальные понятия: `Recipe` пока не реализован. Создавать все будущие классы / таблицы заранее не нужно.

## Правила расчёта блюда

КБЖУ блюда равно сумме КБЖУ вошедших ингредиентов с учётом явно указанных удалённых частей. Значение на 100 г готового блюда рассчитывается как итог блюда, делённый на итоговую массу и умноженный на 100. Значение порции рассчитывается пропорционально её массе либо указанной доле готового блюда. Качество каждого результата не может быть выше худшего качества среди значений, от которых зависит его расчёт.

Потеря воды при приготовлении меняет массу и концентрацию на 100 г, но сама по себе не удаляет калории ингредиентов. Слитый жир / бульон — отдельное явно указанное изменение состава, а не автоматический вывод из уменьшения веса. Промежуточные значения не округляются; округление отображения не меняет исходные данные.

## Исправления дневника

После подтверждения пользователь может исправить массу порции того же продукта / блюда либо убрать ошибочную запись из дневного рациона. Каждая коррекция пересчитывает КБЖУ из исходного подтверждённого снимка, не из уже исправленных значений и не из актуального каталога. Точная новая масса не повышает автоматически качество исходных пищевых данных; приблизительная масса может его снизить.

Исходная порция и исторический предпросмотр сохраняются. Удаление исключает запись из дневного прогресса, а повтор подтверждения сессии её не восстанавливает. Версия записи защищает от перезаписи чужого по времени изменения: при конфликте пользователь сначала видит текущие данные. В текущем шаге API меняет только массу, не название, дату или состав; для ошибочно распознанного продукта можно убрать порцию и внести правильную новой сессией.

## Автономный мобильный режим

9 октября пользователь выбрал первый полноценный Android-клиент с локальными профилями вместо облачного входа. Каждый профиль имеет собственную SQLite-базу, фотографии и настройки на телефоне. Дневник, продукты, собственные блюда и расчёты работают без сервера и сети. Groq вызывается напрямую с личным ключом выбранного профиля, сохранённым в защищённом хранилище телефона.

Это разделение данных, не аутентификация: email/пароль, Google/Apple, синхронизация и перенос между устройствами не реализуются этим режимом. Серверная версия остаётся отдельным вариантом размещения; рабочая серверная база не переносится и не меняется автоматически. Исходные продуктовые правила расчёта, источников и подтверждения одинаковы в обоих вариантах.
