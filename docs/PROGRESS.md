## Этап 6

- добавлены неизменяемые `IngredientDraft`, `DishDraft` и `MealDraft` для структурированного результата разбора;
- черновик хранит несколько блюд, ингредиенты, массы, порции и компактный список вопросов для уточнения;
- `RequiresClarification` вычисляется из наличия вопросов без выдуманных процентов уверенности;
- `FakeMealParser` распознаёт три заранее заданные последовательности событий и явно отклоняет неизвестный сценарий;
- неоднозначный fake-сценарий возвращает вопрос о сухой или готовой массе макарон и оставляет сессию на проверке;
- после добавления ответа новым событием повторный fake-разбор возвращает черновик без вопросов;
- парсер принимает только сессию `ReadyForReview`, не меняет её состояние и не подтверждает результат автоматически;
- результат парсера не содержит `NutritionValues`, `Product`, `DishBatch` или `MealEntry` и не выполняет арифметику КБЖУ;
- консоль сопоставляет распознанные имена с вручную заданным каталогом продуктов, после чего существующий C#-код рассчитывает блюдо и порции;
- консольный демо-сценарий явно принимает ровно одно блюдо и не подтверждает частично обработанный черновик;
- списки внутри черновика копируются и доступны снаружи только для чтения;
- сумма съеденных порций в черновике не может превышать итоговый вес блюда;
- контракт для полностью неполного или противоречивого черновика будет уточнён перед подключением настоящего AI;
- настоящий AI, произвольный разбор текста, поиск продуктов, API, база данных и фотографии не добавлялись.

- направление новой зависимости остаётся односторонним: `Api` → `Domain`;
- `POST /api/meal-drafts/parse` принимает массив накопленных сообщений и возвращает структурированный черновик в JSON;
- отдельные API-контракты защищают внешний JSON-формат от случайных изменений доменных классов;
- `FakeMealParser` зарегистрирован во встроенном контейнере зависимостей как один неизменяемый экземпляр без преждевременного интерфейса;
- понятный и неоднозначный сценарии возвращают `200 OK`, причём вопросы являются частью нормального ответа;
- пустой или некорректный список сообщений возвращает `400 Bad Request`, а неподдерживаемая fake-последовательность — `422 Unprocessable Entity`;
- OpenAPI JSON доступен в режиме разработки по `/openapi/v1.json`, интерактивный Swagger UI — по `/swagger`;
- `Microsoft.AspNetCore.OpenApi` генерирует описание endpoint, а `Swashbuckle.AspNetCore.SwaggerUI` предоставляет только интерактивную страницу;
- официальный OpenAPI-пакет обновлён до `10.0.11` после предупреждения об уязвимой транзитивной зависимости в шаблонной версии `10.0.10`;
- контроллеры, база данных, хранение сессий, авторизация, настоящий AI и новый слой сервисов не добавлялись.

## Этап 8

- добавлены конечные наборы `NutritionSourceKind` и `DataQuality` без выдуманных процентов уверенности;
- `NutritionSource` хранит вид источника, понятное название, качество данных и ссылку на первоисточник, когда она применима;
- ссылка остаётся строкой, потому что ею может быть URL, идентификатор фотографии или запись внешнего сервиса;
- для фотографии ссылка обязательна, а для веб-страницы обязателен абсолютный `http` или `https` URL;
- любой `Product` теперь обязательно создаётся с источником КБЖУ, поэтому потерять происхождение данных по умолчанию нельзя;
- место поиска не подменяет первоначальный источник: сохранённые локально данные внешнего сервиса продолжат ссылаться на этот сервис;
- консольные значения честно отмечены как демонстрационный ручной ввод с неизвестным качеством;
- модель допускает явные значения `Unknown`, но отклоняет несуществующие значения перечислений и пустые обязательные поля;
- добавлен проект `NutriFlow.Infrastructure`, который зависит от `Domain`, а `Domain` по-прежнему ничего не знает о базе данных;
- официальный провайдер `Microsoft.EntityFrameworkCore.Sqlite` 10.0.11 преобразует LINQ-запросы в параметризованный SQL для SQLite;
- EF хранит плоский внутренний `ProductRecord`, а каталог собирает из него проверяемые доменные `Product`, `NutritionValues` и `NutritionSource`;
- первая миграция создаёт таблицу `Products`, индекс нормализованного названия и таблицу истории миграций EF Core;
- локальный `dotnet-ef` 10.0.11 закреплён в tool manifest, а пакет `Microsoft.EntityFrameworkCore.Design` не передаётся потребителям API;
- API автоматически применяет миграции только в `Development`; способ применения миграций при внешнем развёртывании будет выбран отдельно;
- `LocalProductCatalog` сохраняет продукты и выполняет точный поиск после удаления внешних пробелов, канонической Unicode-нормализации и независимого от культуры приведения к верхнему регистру;
- одинаковое название может вернуть несколько вариантов продукта, но последовательная полностью одинаковая повторная запись отклоняется;
- КБЖУ сохраняются SQLite в колонках `TEXT`, чтобы не терять точность `decimal`; сортировку и диапазонный поиск по этим колонкам пока выполнять нельзя;
- `POST /api/products/manual` сохраняет ручной ввод и требует явно передать признак приблизительности;
- `GET /api/products?name=...` возвращает все точные локальные совпадения или пустой список, который позже станет сигналом перейти к внешнему источнику;
- путь к файлу базы настраивается относительно каталога API, файлы SQLite исключены из Git;
- добавлен отдельный проект интеграционных тестов `NutriFlow.Infrastructure.Tests` с настоящими временными SQLite-базами;
- продукт может хранить необязательный штрихкод GTIN длиной 8, 12, 13 или 14 цифр без потери ведущих нулей;
- уникальный индекс штрихкода защищает локальный кэш от повторных записей одного упакованного продукта;
- добавлен HTTP-клиент Open Food Facts v3, который запрашивает только имя и КБЖУ на 100 г, проверяет полноту и разумные границы значений;
- данные Open Food Facts сохраняются с исходной URL и качеством `Unknown`, потому что успешный ответ пользовательской базы сам по себе не является проверкой;
- `ProductLookupService` реализует цепочку `SQLite → Open Food Facts → SQLite`: сеть вызывается только при локальном промахе, валидный результат кэшируется;
- `GET /api/products/barcode/{barcode}` возвращает локальный или внешний продукт и различает неверный штрихкод, отсутствие продукта, неполные данные, сбой и таймаут внешнего сервиса;
- поиск произвольных ингредиентов по названию во внешнем каталоге остаётся отдельной задачей: Product Opener v3 предоставляет надёжный поиск конкретного продукта по штрихкоду, но не обычный полнотекстовый поиск.

## Этап 9

- добавлен единый асинхронный контракт `IMealParser`, у которого есть fake-реализация для локального запуска и OpenAI-реализация для произвольного текста;
- OpenAI Responses API вызывается напрямую стандартным `HttpClient`, поэтому новый NuGet-пакет для AI не понадобился;
- ответ ограничен строгой JSON-схемой, в которой отсутствуют поля КБЖУ: модель извлекает только блюда, ингредиенты, массы, порции и вопросы;
- запросы отправляются с `store: false`, модель и базовый URL настраиваются отдельно, API-ключ читается только из конфигурации или user secrets;
- приложение по умолчанию запускается с `Ai:Provider=Fake`; режим `OpenAI` требует явной настройки ключа и не создаёт скрытой сетевой зависимости;
- черновик теперь различает точную, приблизительную и неизвестную массу ингредиента, итогового блюда и порции;
- неизвестная масса хранится как `null`, поэтому AI не вынужден выдумывать число ради прохождения конструктора;
- на вход HTTP endpoint установлены пределы: до 50 сообщений, до 4000 символов в одном и до 20000 символов суммарно;
- сбой, некорректный структурированный ответ и таймаут AI преобразуются в стабильные ответы `502` и `504`;
- тесты проверяют тело запроса, `store: false`, строгий structured output, отсутствие КБЖУ в схеме, качество масс и ошибочные ответы без настоящего API-ключа.

## Этап 10

- добавлен `POST /api/labels/analyze`, принимающий одну фотографию этикетки через `multipart/form-data`;
- разрешены только JPEG, PNG и WebP до 8 МБ, причём формат проверяется по сигнатуре файла, а не по расширению или одному заголовку `Content-Type`;
- исходное имя файла не участвует в хранении: после успешного анализа создаётся случайная ссылка вида `label-photo:{guid}.jpg`;
- фотографии сохраняются в настраиваемом каталоге `Storage:LabelPhotosPath`, который вместе с SQLite расположен в исключённой из Git папке `NutriFlow.Api/data`;
- OpenAI получает изображение как `input_image` и возвращает отдельный строгий structured output без выдуманных процентов уверенности;
- распознаются данные на 100 г, 100 мл или порцию, но в доменный `Product` можно перейти только из полного, подтверждённого черновика на 100 г;
- отсутствующие и нечитаемые значения остаются `null`, а вопросы возвращаются одним списком;
- в fake-режиме endpoint честно возвращает `503`: случайная фотография не подменяется демонстрационными КБЖУ;
- фотография сохраняется только после успешного AI-ответа; при ошибке формата, отсутствии AI или сбое провайдера файл не остаётся в хранилище;
- модульные тесты покрывают сигнатуры файлов, несовпадение MIME, лимит размера, безопасное имя, AI-запрос с data URL и проверку доменного черновика.
