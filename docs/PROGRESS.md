# Прогресс разработки

Последнее обновление: 5 октября 2026 года.

## Сейчас

Приоритет — бэкенд для мобильного приложения; веб-интерфейс остаётся временным клиентом. Основной сценарий API проверен без браузера. Контракт зафиксирован в `docs/MOBILE_API.md`, правила владения — в `docs/USER_DATA.md`. Создание и дополнение сессии защищены от повторов с `Idempotency-Key`. Постоянный локальный владелец ограничивает сессии, дневник, цели, личные продукты, алиасы, сохранённые блюда и фотографии; новый внешний каталог хранится отдельно как общий. По прямому запросу пользователя добавлены отдельные режимы создания собственного блюда и внесения съеденного в дневник, с переключателем над черновиком. Сервер поддерживает исправление массы и мягкое удаление порций с проверкой ревизии, без изменения исходного подтверждённого снимка. Общая политика запрещает HTTP-кэширование ответов `/api`, включая ошибки. Входа и проверки личности HTTP-клиента пока нет. Пользователь попросил отложить Google- и Apple-вход, требующий настройки провайдеров.

## Среда и репозиторий

- Git-репозиторий инициализирован; ветка `main` отслеживает `origin/main`.
- Установлен .NET SDK 10.0.400; проекты нацелены на .NET 10.
- Локальные host и shared runtime обновлены до 10.0.11.

- направление зависимостей остаётся односторонним: Console → Domain и Tests → Domain;
- добавлены проверки неотрицательных КБЖУ, обязательных имён и объектов, положительных масс, непустого блюда и допустимой порции;
- тестами покрыты сложение и масштабирование КБЖУ, расчёт ингредиента, всего блюда, значений на 100 г, порции и основные ошибочные входные данные;

## Этап 4

## Этап 5

- наружу передаётся коллекция только для чтения, а изменяемый список остаётся внутри сессии;
- консольный сценарий явно показывает, что исходные сообщения пока хранятся без автоматического разбора;
- парсер, структурированный черновик, вопросы, фотографии, AI, API и хранение не добавлялись.

## Этап 6

- добавлены неизменяемые `IngredientDraft`, `DishDraft` и `MealDraft` для структурированного результата разбора;
- черновик хранит несколько блюд, ингредиенты, массы, порции и компактный список вопросов для уточнения;
- `RequiresClarification` вычисляется из наличия вопросов без выдуманных процентов уверенности;
- `FakeMealParser` распознаёт три заранее заданные последовательности событий и явно отклоняет неизвестный сценарий;
- неоднозначный fake-сценарий возвращает вопрос о сухой или готовой массе макарон и оставляет сессию на проверке;
- после добавления ответа новым событием повторный fake-разбор возвращает черновик без вопросов;
- парсер принимает только сессию `ReadyForReview`, не меняет её состояние и не подтверждает результат автоматически;
- результат парсера не содержит `NutritionValues`, `Product`, `DishBatch` или `MealEntry` и не выполняет арифметику КБЖУ;
- консоль сопоставляет распознанные имена с вручную заданным каталогом продуктов, после чего существующий C#-код рассчитывает блюдо и порции;
- консольный демо-сценарий явно принимает ровно одно блюдо и не подтверждает частично обработанный черновик;
- списки внутри черновика копируются и доступны снаружи только для чтения;
- сумма съеденных порций в черновике не может превышать итоговый вес блюда;
- контракт для полностью неполного или противоречивого черновика будет уточнён перед подключением настоящего AI;
- настоящий AI, произвольный разбор текста, поиск продуктов, API, база данных и фотографии не добавлялись.

## Этап 7

- добавлен исполняемый ASP.NET Core-проект `NutriFlow.Api` на .NET 10;
- направление новой зависимости остаётся односторонним: `Api` → `Domain`;
- `POST /api/meal-drafts/parse` принимает массив накопленных сообщений и возвращает структурированный черновик в JSON;
- отдельные API-контракты защищают внешний JSON-формат от случайных изменений доменных классов;
- `FakeMealParser` зарегистрирован во встроенном контейнере зависимостей как один неизменяемый экземпляр без преждевременного интерфейса;
- понятный и неоднозначный сценарии возвращают `200 OK`, причём вопросы являются частью нормального ответа;
- пустой или некорректный список сообщений возвращает `400 Bad Request`, а неподдерживаемая fake-последовательность — `422 Unprocessable Entity`;
- OpenAPI JSON доступен в режиме разработки по `/openapi/v1.json`, интерактивный Swagger UI — по `/swagger`;
- `Microsoft.AspNetCore.OpenApi` генерирует описание endpoint, а `Swashbuckle.AspNetCore.SwaggerUI` предоставляет только интерактивную страницу;
- официальный OpenAPI-пакет обновлён до `10.0.11` после предупреждения об уязвимой транзитивной зависимости в шаблонной версии `10.0.10`;
- контроллеры, база данных, хранение сессий, авторизация, настоящий AI и новый слой сервисов не добавлялись.

## Этап 8

- добавлены конечные наборы `NutritionSourceKind` и `DataQuality` без выдуманных процентов уверенности;
- `NutritionSource` хранит вид источника, понятное название, качество данных и ссылку на первоисточник, когда она применима;
- ссылка остаётся строкой, потому что ею может быть URL, идентификатор фотографии или запись внешнего сервиса;
- для фотографии ссылка обязательна, а для веб-страницы обязателен абсолютный `http` или `https` URL;
- любой `Product` теперь обязательно создаётся с источником КБЖУ, поэтому потерять происхождение данных по умолчанию нельзя;
- место поиска не подменяет первоначальный источник: сохранённые локально данные внешнего сервиса продолжат ссылаться на этот сервис;
- консольные значения честно отмечены как демонстрационный ручной ввод с неизвестным качеством;
- модель допускает явные значения `Unknown`, но отклоняет несуществующие значения перечислений и пустые обязательные поля;
- добавлен проект `NutriFlow.Infrastructure`, который зависит от `Domain`, а `Domain` по-прежнему ничего не знает о базе данных;
- официальный провайдер `Microsoft.EntityFrameworkCore.Sqlite` 10.0.11 преобразует LINQ-запросы в параметризованный SQL для SQLite;
- EF хранит плоский внутренний `ProductRecord`, а каталог собирает из него проверяемые доменные `Product`, `NutritionValues` и `NutritionSource`;
- первая миграция создаёт таблицу `Products`, индекс нормализованного названия и таблицу истории миграций EF Core;
- локальный `dotnet-ef` 10.0.11 закреплён в tool manifest, а пакет `Microsoft.EntityFrameworkCore.Design` не передаётся потребителям API;
- API автоматически применяет миграции только в `Development`; способ применения миграций при внешнем развёртывании будет выбран отдельно;
- `LocalProductCatalog` сохраняет продукты и выполняет точный поиск после удаления внешних пробелов, канонической Unicode-нормализации и независимого от культуры приведения к верхнему регистру;
- одинаковое название может вернуть несколько вариантов продукта, но последовательная полностью одинаковая повторная запись отклоняется;
- КБЖУ сохраняются SQLite в колонках `TEXT`, чтобы не терять точность `decimal`; сортировку и диапазонный поиск по этим колонкам пока выполнять нельзя;
- `POST /api/products/manual` сохраняет ручной ввод и требует явно передать признак приблизительности;
- `GET /api/products?name=...` возвращает все точные локальные совпадения или пустой список, который позже станет сигналом перейти к внешнему источнику;
- путь к файлу базы настраивается относительно каталога API, файлы SQLite исключены из Git;
- добавлен отдельный проект интеграционных тестов `NutriFlow.Infrastructure.Tests` с настоящими временными SQLite-базами;
- продукт может хранить необязательный штрихкод GTIN длиной 8, 12, 13 или 14 цифр без потери ведущих нулей;
- уникальный индекс штрихкода защищает локальный кэш от повторных записей одного упакованного продукта;
- добавлен HTTP-клиент Open Food Facts v3, который запрашивает только имя и КБЖУ на 100 г, проверяет полноту и разумные границы значений;
- данные Open Food Facts сохраняются с исходной URL и качеством `Unknown`, потому что успешный ответ пользовательской базы сам по себе не является проверкой;
- `ProductLookupService` реализует цепочку `SQLite → Open Food Facts → SQLite`: сеть вызывается только при локальном промахе, валидный результат кэшируется;
- `GET /api/products/barcode/{barcode}` возвращает локальный или внешний продукт и различает неверный штрихкод, отсутствие продукта, неполные данные, сбой и таймаут внешнего сервиса;
- поиск произвольных ингредиентов по названию во внешнем каталоге остаётся отдельной задачей: Product Opener v3 предоставляет надёжный поиск конкретного продукта по штрихкоду, но не обычный полнотекстовый поиск.

## Этап 9

- добавлен единый асинхронный контракт `IMealParser`, у которого есть fake-реализация для локального запуска и OpenAI-реализация для произвольного текста;
- OpenAI Responses API вызывается напрямую стандартным `HttpClient`, поэтому новый NuGet-пакет для AI не понадобился;
- ответ ограничен строгой JSON-схемой, в которой отсутствуют поля КБЖУ: модель извлекает только блюда, ингредиенты, массы, порции и вопросы;
- запросы отправляются с `store: false`, модель и базовый URL настраиваются отдельно, API-ключ читается только из конфигурации или user secrets;
- приложение по умолчанию запускается с `Ai:Provider=Fake`; режим `OpenAI` требует явной настройки ключа и не создаёт скрытой сетевой зависимости;
- черновик теперь различает точную, приблизительную и неизвестную массу ингредиента, итогового блюда и порции;
- неизвестная масса хранится как `null`, поэтому AI не вынужден выдумывать число ради прохождения конструктора;
- на вход HTTP endpoint установлены пределы: до 50 сообщений, до 4000 символов в одном и до 20000 символов суммарно;
- сбой, некорректный структурированный ответ и таймаут AI преобразуются в стабильные ответы `502` и `504`;
- тесты проверяют тело запроса, `store: false`, строгий structured output, отсутствие КБЖУ в схеме, качество масс и ошибочные ответы без настоящего API-ключа.

## Этап 10

- добавлен `POST /api/labels/analyze`, принимающий одну фотографию этикетки через `multipart/form-data`;
- разрешены только JPEG, PNG и WebP до 8 МБ, причём формат проверяется по сигнатуре файла, а не по расширению или одному заголовку `Content-Type`;
- исходное имя файла не участвует в хранении: после успешного анализа создаётся случайная ссылка вида `label-photo:{guid}.jpg`;
- фотографии сохраняются в настраиваемом каталоге `Storage:LabelPhotosPath`, который вместе с SQLite расположен в исключённой из Git папке `NutriFlow.Api/data`;
- OpenAI получает изображение как `input_image` и возвращает отдельный строгий structured output без выдуманных процентов уверенности;
- распознаются данные на 100 г, 100 мл или порцию, но в доменный `Product` можно перейти только из полного, подтверждённого черновика на 100 г;
- отсутствующие и нечитаемые значения остаются `null`, а вопросы возвращаются одним списком;
- в fake-режиме endpoint честно возвращает `503`: случайная фотография не подменяется демонстрационными КБЖУ;
- фотография сохраняется только после успешного AI-ответа; при ошибке формата, отсутствии AI или сбое провайдера файл не остаётся в хранилище;
- модульные тесты покрывают сигнатуры файлов, несовпадение MIME, лимит размера, безопасное имя, AI-запрос с data URL и проверку доменного черновика.

## Этап 11

- добавлена сохраняемая `MealSession`: исходные сообщения, структурированный черновик, дата, состояние и серверный снимок предпросмотра переживают перезапуск API;
- сервис сценария сопоставляет ингредиенты с локальным каталогом и вызывает только доменные `DishIngredient` и `DishBatch` для расчёта ингредиентов, блюда, значений на 100 г и порций;
- отсутствие массы, итогового веса или порции, вопрос парсера, ненайденный либо действительно неоднозначный продукт блокируют подтверждение и возвращаются как понятные проблемы;
- среди нескольких источников приложение автоматически предпочитает более качественные данные; одинаково качественные варианты с разными КБЖУ не выбираются наугад;
- каждый предпросмотр получает SHA-256-токен, вычисленный из рассчитанного снимка; если каталог изменился до подтверждения, старый токен отклоняется и пользователь видит обновлённые значения;
- подтверждение принимает только идентификатор сессии и токен, не доверяет присланным клиентом КБЖУ и атомарно сохраняет снимки всех съеденных порций;
- конкурентные и повторные подтверждения не создают дубликаты: состояние сессии захватывается условным обновлением внутри одной SQLite-транзакции;
- добавлены сохраняемые дневные цели и выдача съеденных, оставшихся и превышенных КБЖУ по выбранной дате;
- результат распознавания этикетки можно после проверки сохранить как продукт с источником `LabelPhoto` и ссылкой на исходную фотографию;
- в fake-режиме идемпотентно добавляются два явно обозначенных демонстрационных продукта, поэтому основной сценарий запускается без ключа и внешней сети;
- API применяет миграции при старте во всех окружениях по настраиваемому флагу, а новая миграция создаёт таблицы `MealSessions`, `MealEntries` и `DailyGoals`;
- добавлен адаптивный веб-интерфейс без Node.js, CDN и отдельной сборки: лента сообщений, предпросмотр, вопросы, каталог, подтверждение и дневной баланс работают с того же origin;
- отдельный проект HTTP-тестов поднимает настоящий ASP.NET Core-конвейер и временную SQLite-базу;
- тестами проверены полный HTTP-поток, точная арифметика, устаревший предпросмотр, уточнение, обновление каталога, конкурентное подтверждение, происхождение этикетки и выдача главной страницы.

## Подготовка к демонстрации и развёртыванию

- корневой `README.md` описывает продукт, архитектуру, быстрый fake-сценарий, подключение OpenAI, HTTP API, конфигурацию, ограничения и команды проверки;
- SDK закреплён на feature band `10.0.400`, чтобы локальный запуск и CI использовали совместимый набор компилятора и MSBuild;
- разрешённый граф NuGet-зависимостей закреплён отдельным `packages.lock.json` для каждого проекта; CI и Docker восстанавливают его в `--locked-mode`;
- добавлены отдельные liveness- и readiness-маршруты; readiness проверяет соединение с SQLite и отсутствие неприменённых миграций с таймаутом пять секунд;
- ответы защищены базовыми browser security headers, а Swagger остаётся доступным в `Development`, где его встроенный скрипт несовместим со строгой CSP приложения;
- операции, способные вызвать внешние сервисы, ограничены двенадцатью запросами в минуту с IP; отказ возвращает `429 ProblemDetails` и `Retry-After` при наличии метаданных лимитера;
- GitHub Actions восстанавливает инструменты и пакеты, собирает Release, запускает тесты, проверяет форматирование, EF-модель, уязвимые зависимости и сборку Docker-образа;
- multi-stage Dockerfile публикует только API и его зависимости, запускает процесс без root и сохраняет SQLite и фотографии в volume `/data`;
- документация явно фиксирует отсутствие аутентификации, особенности trusted proxy и ограничение SQLite одним экземпляром.

## Стабилизация веб-сценария

- интерфейс получает возможности текущего AI-провайдера через `/api/capabilities`, явно показывает Fake-режим и не предлагает недоступную отправку фотографий;
- незавершённая сессия восстанавливается в браузере, её дата блокируется до подтверждения, а запросы дневного прогресса защищены от устаревших ответов при быстрой смене дня;
- предпросмотр сохраняет частичные расчёты: известные ингредиенты дают итог блюда даже до указания финального веса или порции;
- явно удалённая масса хранится отдельно и вычитается доменным кодом; порции поддерживают как массу, так и долю готового блюда;
- качество итогового КБЖУ блюда, значения на 100 г и порций вычисляется из использованных источников и масс и показывается до подтверждения;
- подтверждённая запись сохраняет худшую категорию качества, а фотографию этикетки-источник можно открыть по непрозрачной same-origin ссылке;
- локальные алиасы связывают формулировку ингредиента с продуктом по штрихкоду, а более качественные данные могут заменить менее качественный результат внешнего каталога без потери прежнего имени;
- условные обновления по `previewToken` не дают устаревшему запросу перезаписать новую версию сессии или подтверждённый результат; установка дневной цели также выдерживает конкурентное создание;
- границы КБЖУ на 100 г проверяются доменом, AI-ответы защищены от `null`-элементов и путаницы kcal/kJ, а Open Food Facts не может вернуть данные для другого или некорректного штрихкода;
- миграция `HardenProductResolutionAndMealQuality` добавляет алиасы продуктов и качество дневных записей, сохраняя совместимость со старыми JSON-черновиками.

## Подключение Groq

- добавлены отдельные адаптеры Groq для разбора сообщений и фотографий этикеток через Chat Completions API;
- запрос использует system/user messages, строгую JSON-схему, отключённый streaming и принимает только полностью завершённый ответ с `finish_reason=stop`;
- модели текста и изображений настраиваются независимо, а ключ читается из конфигурации или .NET User Secrets и отсутствует в репозитории;

- ограничения длины, количества элементов и бизнес-инварианты повторно проверяются кодом, а не доверяются одному ответу модели;

## Идемпотентное создание сессии

- `POST /api/meal-sessions` принимает необязательный заголовок `Idempotency-Key` с UUID; без него прежнее поведение и временный веб-клиент не изменились;
- при наличии ключа требуется явная `mealDate`, чтобы повтор через полночь не менял дату запроса;
- первый запрос возвращает `201`, повтор исходных сообщений и даты — `200` с тем же `id` и текущим состоянием сессии без повторного AI-разбора; использование ключа с другими исходными данными возвращает `409`;
- необязательный заголовок объявлен в OpenAPI, чтобы его видели Swagger и будущие клиенты, создаваемые по контракту;
- ключ и SHA-256 отпечаток исходного запроса сохраняются отдельно от изменяемой истории сообщений; уникальный индекс SQLite не допускает двойной записи при одновременных запросах;
- миграция добавляет nullable-поля и сохраняет старые строки; тест проверяет обновление существующей базы и возможность нескольких сессий без ключа;
- два строго одновременных первых запроса могут оба вызвать AI до записи, хотя сохраняется только одна сессия; устранение двойного внешнего вызова потребовало бы отдельного механизма резервирования;
- новые NuGet-пакеты, пользователи, авторизация и изменения веб-клиента не добавлялись; повтор дополнения сообщения был выполнен следующим отдельным шагом.

## Идемпотентное дополнение сессии

- `POST /api/meal-sessions/{id}/messages` принимает необязательный `Idempotency-Key` с UUID; без него каждое успешное обращение по-прежнему добавляет сообщение;
- повтор с тем же ключом и текстом возвращает `200` с текущей сессией без повторного добавления и разбора, в том числе после перезапуска сервера, других сообщений или подтверждения;
- тот же ключ с другим текстом возвращает `409`, а новый ключ с тем же текстом обозначает новое сообщение; область действия ключа — одна сессия;
- миграция добавляет в `MealSessions` JSON-поле с пустым значением по умолчанию для старых строк; в нём хранятся только UUID и SHA-256 отпечатки текста, максимум 50 записей;
- история, черновик, предпросмотр и ключ повтора записываются одним условным обновлением SQLite. При гонке сохраняется одно дополнение; проигравший запрос сверяет ключ с уже сохранённым результатом;
- строго одновременные запросы могут оба вызвать AI до записи в базу, хотя сообщение сохраняется только один раз; резервирование AI-вызова не входит в этот небольшой этап;
- добавлены HTTP- и инфраструктурные тесты повтора, конфликта, гонки, перезапуска, старых строк, пределов и повреждённого хранилища; новых NuGet-пакетов, пользователей и авторизации нет.

## Локальный владелец ядра дневника

- новая таблица `Users` хранит внутренний `Guid`, время создания и признак одного локального владельца установки; это идентификатор данных, а не пароль или проверка личности;
- миграция создаёт для каждой базы собственный UUID локального владельца, относит к нему старые сессии и дневные цели, меняет ключ цели на `(UserId, Date)` и ограничивает уникальность `Idempotency-Key` парой `(UserId, IdempotencyKey)`;
- подтверждённые порции сохраняют связь с сессией и наследуют её владельца; миграция не пересчитывает их КБЖУ и качество;
- `MealSessionStore` и `DailyDiaryStore` выбирают локального владельца на сервере и фильтруют чтение, изменение, подтверждение и повторы по его ID; тесты хранилищ проверяют двух владельцев с одинаковой датой и ключом;
- продукты, алиасы и фотографии пока не привязаны к владельцу, а HTTP-клиент не проходит аутентификацию. Следовательно, этот шаг не даёт многопользовательской защиты и не разрешает публичное размещение API;
- перед миграцией сделана локальная резервная копия базы и трёх фотографий. Миграция отдельно применена к копии реальной базы: число сессий, порций, целей и продуктов осталось `5 / 16 / 2 / 7`, SQLite `integrity_check` вернул `ok`, нарушений внешних ключей нет, исходный файл не менялся;
- EF Core предупредил, что перестройка таблиц SQLite имеет не полностью транзакционный участок; исходная резервная копия остаётся необходимой. Обратная миграция запрещена, потому что объединение целей разных владельцев по одной дате могло бы потерять данные. Новые NuGet-пакеты не добавлялись.

## Личный и общий каталог

Миграции применены только к `data/validation/catalog-migration-d303702f980e469b8cf87208c15f3225.db`: количества сессий / порций / целей / продуктов / алиасов остались `5 / 16 / 2 / 7 / 0`; отпечаток прежних полей каталога, порций и целей совпал (`2675FF9B92AF...`), все семь старых продуктов личные, `integrity_check` вернул `ok`, нарушений внешних ключей нет;

## Разделение ошибок парсера и хранения

- исправлена неверная классификация `InvalidDataException`: при повторном создании сессии или добавлении сообщения повреждённые локальные JSON выдавались за неверный ответ AI с `502`;
- ошибка помечается `MealParserResponseException` только вокруг вызова парсера; endpoints создания и дополнения перехватывают этот тип. Ошибки чтения SQLite обрабатываются стандартным серверным обработчиком с `500`, как при GET и подтверждении;
- до исправления HTTP-проверки воспроизвели шесть ошибочных ответов `502`; после исправления все 14 новых проверок проходят. Они сравнивают строки сессий и дневника до и после запроса, число вызовов парсера и отсутствие внутренних деталей в Production-ответе;
- настоящий неверный ответ парсера сохраняет `502`, повреждение сообщений, черновика или ключей повторов — `500`. Мобильный контракт дополнен этим различием;
- новые функции, комментарии, пакеты и миграции не добавлялись; исходная база и фотографии сохранили прежние SHA-256.

## Проверка сохранённого предпросмотра

- закрыта неполная проверка `PreviewJson`: подтверждённые сессии, повторы подтверждения и ответы с устаревшим токеном больше не возвращают пустые элементы списков, пустые обязательные списки и имена, отрицательные значения или неизвестные названия качества;

- до исправления 24 из 32 HTTP-проверок воспроизвели неверные ответы `200` / `409`. После исправления и добавления проверки границы `decimal` все 33 новых теста проходят; сравнение всех столбцов сессий и дневника подтверждает отсутствие изменений и дублей при чтении, ошибке и повторе;

## Создание собственного блюда отдельно от дневника

- `MealSessionPurpose` разделяет намерения `Diary` и `CreateDish`, независимо от состояний черновика. Режим сохраняется в SQLite; прежние сессии и запросы без нового поля остаются `Diary`. Формат отпечатка исходного запроса и токена прежнего режима сохранён; смена режима с тем же ключом повтора отклоняется.
- `CreateDish` требует одно блюдо с названием, ингредиентами, найденными продуктами и готовым весом. Порция не нужна; сведения о съеденном в этом режиме не создают записи дневника. Сервер блокирует несколько блюд, недопустимое нормализованное имя и КБЖУ, вышедшие за ограничения продукта, до подтверждения.
- `SavedDishStore` атомарно подтверждает сессию и создаёт личный снимок блюда. Повторы, перезапуск и конкурентные подтверждения возвращают тот же результат; совпавшее собственное имя не перезаписывает данные, а возвращает `409` с возможностью уточнить название. `DailyDiaryStore` отдельно запрещает запись сессии `CreateDish` в дневник.

## Исправление массы и удаление порций дневника

- По запросу продолжить серверную разработку выполнен один шаг управления уже внесёнными порциями, без нового интерфейса, мобильного проекта, входа или публичного размещения API.
- Ответы дневного прогресса и подтверждения содержат ID и ревизию активной записи. `GET /api/meal-entries/{id}` возвращает текущую порцию с `ETag`; `PUT` исправляет массу и качество её ввода, `DELETE` исключает запись из дневника.
- `MealEntry.WithWeight` выполняет пропорциональный расчёт обычным C#-кодом. Хранилище каждый раз использует исходные массу и КБЖУ, а не результат прошлой правки или изменившийся каталог; промежуточные значения не округляются. Приблизительная масса понижает качество, точная не повышает достоверность исходных приблизительных или неизвестных КБЖУ.
- Новая таблица `MealEntryAdjustments` хранит одно текущее исправление или отметку удаления на порцию. Исходные `MealEntries` и исторические предпросмотры не переписываются. Старые порции читаются с ревизией `0`; это не история всех промежуточных правок.
- `PUT` и `DELETE` требуют одну каноническую ревизию в кавычках в заголовке `If-Match`: отсутствие даёт `428`, неверный формат — `400`, устаревшая ревизия активной порции — `412`. Изменение начинает транзакцию до чтения, проверяет владельца через подтверждённую сессию `Diary` и атомарно повышает ревизию.
- Чужие и отсутствующие записи возвращают `404`; удалённая недоступна для чтения и изменения. Повторное удаление собственной удалённой порции с допустимым заголовком возвращает `204` без новой правки. Повторное подтверждение сессии возвращает только текущие активные порции и не восстанавливает удалённые.

Проверены арифметика и качество, точность относительно исходного снимка, владельцы, перезапуск, повреждённые данные, переполнение, откат при сбое и конкурентные пары исправление / исправление, исправление / удаление, удаление / удаление. Новых пакетов и обычных комментариев нет.

## Единая политика HTTP-кэша API

- Выполнен один небольшой серверный шаг без новых функций клиента, пакетов, миграций или обычных комментариев. Причина — прежде запрет кэширования был только у фотографий и ответов отдельных порций, но не у личных сессий, дневного баланса и сохранённых блюд.
- В `ApplicationSetup` перед обработчиком исключений регистрируется middleware для сегмента `/api`. `Response.OnStarting` устанавливает `Cache-Control: private, no-store` непосредственно перед отправкой заголовков, включая ответы после очистки при `500`, ошибки привязки, `429` и неизвестные API-маршруты.
- Дублирующие заголовки убраны из обработчиков порций и фотографий; лишний параметр `HttpResponse` у выдачи фото удалён. `ETag` и `If-Match` порций, диапазонные ответы фото и статические условные запросы сохранены. Swagger, OpenAPI, `/health`, `/apiary` и `/api-other` не получают общую политику API.
- Добавлены 23 HTTP-проверки. До исправления 14 проверок API воспроизвели отсутствие полной политики; отдельное исходное предположение теста о Swagger уточнено, поскольку он уже устанавливает собственный `private` без `no-store`. После исправления все 23 проходят.
- Проверены создание, чтение и подтверждение сессии, дневная цель, исправление и удаление порции, `ETag`, ответы `400`, `404`, `412`, `415`, `428`, `429`, `500`, `503`, верхний регистр `/API`, маршруты вне API и статический `304`. Прежние тесты фотографий повторно проверили содержимое и диапазонный `206`.
- Отдельный Production / Fake API запущен с отключёнными миграциями и демо-наполнением на прежней проверочной копии. Настоящие HTTP-запросы подтвердили `200` для возможностей, дневника и сохранённых блюд, `404` для неизвестного `/API`, `400` для неверной даты, `428` для отсутствующей ревизии и `206` для фото с общей политикой. JavaScript сохранил условный `304` без политики API. Порядок директив заголовка в проверочной команде разобран стандартным HTTP-парсером: `no-store, private` и `private, no-store` равнозначны.
- Проверочный API остановлен. Настоящие внешние сервисы не вызывались; SHA-256 рабочей базы и трёх фотографий прежние. Правило не отключает каталог SQLite, не удаляет данные, явно сохранённые клиентом, и не заменяет аутентификацию или HTTPS.

## Следующий шаг

Два режима ввода, собственные сохранённые блюда, исправление массы и мягкое удаление порций реализованы и проверены. Рабочая база не обновлялась автоматически агентом; резервная копия сделана, переход проверен на копии. При обычном запуске API применит миграции: до него проверьте пути рабочей базы и фотографий. Нужна ручная приёмка собственного названного блюда и фразы о его порции с настроенным Groq, а также старых этикеток и сохранения нового фото. Серверные операции с порциями можно проверить через Swagger; кнопок временного клиента пока нет. Пользователь пока не может провести ручную приёмку, она отложена и не заменена утверждением о проверке настоящего Groq.

Для продолжения серверной подготовки рекомендован отдельный небольшой шаг — воспроизводимая парная резервная копия SQLite и фотографий. Сейчас миграции выполняются автоматически при старте, а копирование описано как ручное действие; данные должны быть защищены перед изменением схемы. Реализация резервного копирования и восстановления в текущий шаг не входит.

Выбор схемы входа для мобильного клиента остаётся отдельной темой. Google / Apple отложены по прежней просьбе; настройки провайдеров, настоящая аутентификация и защищённое развёртывание необходимы перед доступом других пользователей. Новые изменения начинаются только по команде пользователя; политика HTTP-кэша не подтверждает готовность публичного API.
