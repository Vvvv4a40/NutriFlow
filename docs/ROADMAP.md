# Дорожная карта NutriFlow

Дорожная карта предварительная. Этапы меняются только при наличии конкретной причины, которую нужно зафиксировать и объяснить.

9 октября приоритет изменён по прямому запросу пользователя: нужен самостоятельный Android APK для реального использования вместо дальнейших попыток установить iOS через Windows. Пользователь выбрал локальные профили и личный Groq-ключ, а не облачный аккаунт. Текущий шаг — автономный дневник, каталог, собственные блюда, текст/этикетка/голос, изоляция SQLite и постоянная подпись Android. Серверное размещение и HTTP-клиент не являются условием этого APK; облачная аутентификация и синхронизация остаются отдельными будущими решениями. [Установка и ограничения](ANDROID_INSTALLATION.md). Новая версия iOS пока не проверена.

Серверная логика и рабочая база не менялись. Apple-подпись / способ установки и подключение мобильного экрана к API не подменяются успешным симулятором или серверным CI.

Небольшой мобильный шаг Release-сборки `ios-arm64` завершён: [run 37773708893](https://github.com/Vvvv4a40/NutriFlow/actions/runs/37773708893) подтвердил реальную Mono AOT / LLVM-компиляцию без интерпретатора, 0 предупреждений / ошибок, платформу `IOS`, AOT-данные и публикацию артефакта. Новый workflow изолирует device lock; настоящий NuGet-граф сохранён после проверки скачанного артефакта, версии пакетов совпадают с симуляторными. SDK / пакеты не обновлялись, API-клиент и подпись / установка не добавлены. Это проверенная компиляция, не установочный IPA или проверка Release на телефоне.

Пользователь выбрал [бесплатный AltStore Classic через Windows](IOS_INSTALLATION.md), с семидневным сроком и зависимостью обновления от AltServer. Скачанная IPA отдельно сверена на Windows. Исходный unsigned verifier не ослаблялся; Apple Account / ключи / профили, установки программ и операции на телефоне в CI не добавлены. Локальную подпись, запуск и обновление на своём iPhone пользователь проверяет отдельно. Подключение мобильного клиента к API остаётся следующим продуктовым шагом, не частью упаковки.

0. **Проверка среды и минимальный проект** — solution, консольный проект, документация, успешные сборка и запуск.
1. **Один продукт** — расчёт КБЖУ продукта заданной массы в консоли.
2. **Блюдо и порция** — несколько ингредиентов, итоговый вес блюда и съеденная порция.
3. **Доменное ядро и тесты** — выделение расчётной модели и xUnit-тесты.
4. **Дневной прогресс** — цель, съеденные порции и остаток КБЖУ.
5. **Сессия ввода** — `CaptureSession`, `InputEvent` и состояния черновика без AI.
6. **Имитация AI-разбора** — `FakeMealParser` со структурированным результатом.
7. **ASP.NET Core API** — HTTP API и ручная проверка через Swagger.
8. **Хранение и поиск продуктов** — сначала происхождение и качество КБЖУ, затем локальная БД и обращение к внешним источникам.
9. **Разбор текста с AI** — строго структурированный ответ модели.
10. **Фотография этикетки** — загрузка и извлечение пищевой ценности.
11. **Пользовательский интерфейс** — дневной план и подтверждение результатов.
12. **Дальнейшее развитие** — голос, приблизительная оценка готовой еды и мобильный клиент.

Цель проекта — **бэкенд для мобильного приложения**. Существующий веб-интерфейс остаётся временным клиентом для проверки. Приоритет уточнён пользователем: серверные сценарии и HTTP-контракт должны работать независимо от браузера; развитие веб-функций не является следующим этапом.

Текущая версия: основной серверный сценарий от сообщений до подтверждённого дневника реализован и прошёл независимую HTTP-проверку, в том числе в Production и после перезапуска. [Контракт API для мобильного клиента](MOBILE_API.md) фиксирует возможности и ограничения. Сборка проверяется CI и готова к контейнеризации, но публичный многопользовательский сервис ещё не готов.

5 октября по прямому запросу пользователя добавлен небольшой отдельный шаг перед выбором входа: разделение создания собственного блюда и внесения съеденного в дневник. `CreateDish` сохраняет один проверенный состав и КБЖУ без дневниковой записи; `Diary` использует сохранённое блюдо по названию. Временный клиент получил переключатель, мобильный API — поле `purpose` и чтение сохранённых блюд. Причина изменения приоритета — необходимость повторно использовать собственные блюда естественным вводом. Полноценные шаблоны `Recipe`, планирование будущих приёмов пищи и учёт остатков этим шагом не реализуются.

По следующей просьбе доделать серверную часть перед мобильным клиентом приоритетом стало исправление ошибок дневника. Добавлен отдельный серверный шаг: ID / версия порции, коррекция её массы из исходного снимка и мягкое удаление с защитой `If-Match`. Причина — подтверждённая ошибка не должна навсегда менять дневной баланс. Веб-кнопки, изменение состава / даты и восстановление записи не реализуются заранее; вход и размещение остаются отдельными задачами.

Следующим небольшим серверным шагом закрывается неполная политика HTTP-кэша: `private, no-store` действует на все ответы `/api`, а не только на фото и отдельные порции. Причина — личные сессии и дневной баланс не должны сохраняться HTTP-кэшами или выдаваться устаревшими после исправления. Новых продуктовых функций, миграций и изменений временного интерфейса нет; это не заменяет будущую аутентификацию и защищённое размещение.

Следующим отдельным шагом реализовано воспроизводимое парное резервное копирование SQLite и фотографий через `NutriFlow.Tools`: offline-создание, manifest и проверка целостности. Причина — автоматическим миграциям при запуске нужна проверяемая копия данных. Исходное хранилище не меняется, новые пакеты и миграции не добавляются.

После копирования проверен запуск обновлённого API на отдельном восстановленном хранилище: миграции старой схемы, дневные итоги, фото и повторы подтверждения. Добавлены автоматические HTTP-тесты и инструкция пробного запуска в `BACKUPS.md`. Причина — проверка целостности файлов сама по себе не подтверждает их совместимость с новым API. Рабочая установка и архив не подменяются; автоматическое восстановление поверх оригинала, расписание и размещение остаются отдельными задачами.

Следующим небольшим серверным шагом общие настройки перестали молча выбирать Fake и добавлять демо-продукты в Production. Локальный сценарий перенесён в Development-конфиг; выбор провайдера, наличие ключа и флаг демо проверяются до работы с хранилищем. Docker и EF-проверка CI используют ту же политику. Причина — пробный запуск ранее был безопасен только благодаря ручным переопределениям. Это не аутентификация, не проверка настоящего ключа у провайдера и не готовность публичного сервиса.

Следующим отдельным шагом защищён состав пакета приложения: Web SDK ранее включал JSON-манифесты резервных копий из `data`, независимо от `.gitignore` и `.dockerignore`. В API добавлены исключения SDK, контекст Docker согласован с ними, изолированная проверка публикации с искусственными приватными файлами включена в CI. Причина — личное хранилище и секреты не должны распространяться вместе с кодом. Новые продуктовые функции, пакеты и миграции не добавляются; публичное размещение по-прежнему требует аутентификации.

Следующим небольшим шагом проверена устойчивость внешних HTTP-вызовов: таймауты и отмена при зависании заголовков / тела, внешний `429`, отсутствие повторов и незавершённых записей. Добавлены тесты шести адаптеров и шести маршрутов API на управляемом транспорте. Причина — мобильный клиент должен отличать собственный лимит NutriFlow, сбой внешнего сервиса и отмену запроса. Рабочий код уже соблюдает этот контракт и не менялся; новые пакеты, функции и настоящие AI-вызовы не добавлялись.

После единичного невоспроизведённого `500` улучшена диагностика API-тестов: исключения собираются отдельно для каждого сервера и выводятся только при несовпадении ожидаемого HTTP-статуса; добавлен параллельный запуск четырёх независимых серверов. Причина — успешный повтор не объясняет первоначальную ошибку. Два новых полных прогона прошли без отключения параллелизма, но исходная причина остаётся неизвестной; рабочий код, пакеты и миграции не менялись.

Следующим небольшим шагом добавлена команда `restore` в `NutriFlow.Tools`: восстановление проверенной парной копии в ещё не существующий каталог. Причина — ручной перенос базы и фото мог оставить неполный результат или перепутать архив и рабочую копию. Архив проверяется до / после копирования, отдельно сверяются записанные файлы; существующее назначение отклоняется, API и миграции не запускаются. HTTP-тесты обновления используют ту же логику. Рабочее хранилище не перезаписывается.

После восстановления сверены реальные endpoints / DTO, 21 операция OpenAPI и мобильное руководство. Добавлены восемь регрессионных проверок описания контракта; документация дополнена исправлением `NeedsProducts`, каталогом, алиасами, ответами фотографий и списком ручной приёмки. Причина — мобильному клиенту нужен полный сценарий, а не только перечень маршрутов.

Отдельным следующим шагом исправлены обнаруженные метаданные: оба MIME / тела `409` подтверждения, фото `200` / `206` и пустой `416`, четыре недостающих `415`, строковые defaults enum. Схемы `decimal` отличают числовые ответы от совместимого ввода `number|string`; настройки JSON и формулы не меняются. Добавлены 14 проверок метаданных и фактического HTTP-поведения. Причина — генератор клиента должен получать корректное описание, а не менять приложение ради него. Новые функции, вход и размещение не добавлены. Перед нативным клиентом остаются ручная приёмка на отдельной рабочей копии и выбор клиентского стека; автоматически сгенерированный SDK и настоящее устройство этим шагом не проверялись.

Перед ручной приёмкой добавлена повторяемая команда `scripts/Test-MealWorkflow.ps1` и шаг CI. Причина — встроенные HTTP-тесты не заменяют запуск отдельного серверного процесса и проверку сохранения после его остановки. На новом искусственном хранилище с Fake проверяются создание блюда, его порция в дневнике, дробные числа, повторы и перезапуск. Рабочие данные и настоящие провайдеры не используются. Следующий шаг остаётся прежним: ручная приёмка Groq на отдельной копии и выбор мобильного стека; новые серверные функции этим изменением не добавляются.

6 октября выбран нативный .NET MAUI с C# / XAML, сначала Android. Подготовлен минимальный клиент в `mobile/` с отдельным solution, чтобы не навязывать серверу Android workloads.
