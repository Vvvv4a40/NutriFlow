# Пользователи и владение данными

Статус: внутренний локальный владелец уже хранится в SQLite. Сессии, записи дневника, цели, личные продукты, алиасы и фотографии ограничены владельцем в хранилищах; общий каталог отделён от личного. Внешнего входа и проверки личности клиента нет. Текущий API остаётся однопользовательским и не должен открываться в интернет для других пользователей.

## Что означает API

API — Application Programming Interface, программный интерфейс. В NutriFlow это набор HTTP-запросов к серверу: клиент отправляет сообщение или запрашивает дневник, сервер отвечает данными в JSON. Мобильное приложение рисует экраны, а C#-сервер хранит данные, вызывает AI и рассчитывает КБЖУ. Существующий веб-клиент пользуется тем же API.

Пример: приложение отправляет `GET /api/daily-progress/2026-09-28`, сервер возвращает цель, съеденные порции и остаток КБЖУ. Это вызов серверной функции через сеть, а не открытие страницы сайта.

Сейчас `localhost:5198` относится к компьютеру, на котором запущен API. Развёртывание — запуск сервера на доступном телефону хосте. Публичная доступность означает, что до адреса можно обратиться из интернета; она не должна означать доступ к чужому дневнику. Для удалённого доступа нужны защищённое соединение и отдельные проверки личности и прав. Их реализация не входит в текущий шаг.

## Вход и права — разные задачи

- Аутентификация отвечает на вопрос «кто делает запрос?». В будущем Google или Apple могут подтвердить личность пользователя.
- Авторизация отвечает на вопрос «к каким данным этому пользователю разрешён доступ?». Эти правила определяет NutriFlow, а не Google или Apple.

Кнопка входа сама по себе не обеспечит права на данные и фотографии. Обе задачи должны работать вместе до открытия доступа другим людям.

## Учётная запись NutriFlow

Рекомендуется собственный постоянный `UserId` типа `Guid`. Это внутренний идентификатор владельца данных, независимый от способа входа. UUID не является паролем или доказательством личности.

Внутренняя запись содержит `Id`, `CreatedAtUtc`, признак нынешнего локального владельца и `LegacyLabelPhotosImported` — отметку однократного переноса старых файлов. Эти признаки нужны для перехода старой базы, а не для входа. Паролей, ролей, подписок и социальных профилей нет.

При подключении внешнего входа проверенная внешняя личность сопоставляется с внутренним пользователем. Для этого понадобится связь `UserId` с парой `Issuer` и `Subject`: кто выдал подтверждение и какого пользователя он идентифицировал. Одна внешняя личность не может принадлежать нескольким аккаунтам NutriFlow.

Email не использовать как основной идентификатор и не объединять Google- и Apple-аккаунты автоматически по совпавшей почте. Связывание второго способа входа требует отдельного подтверждения контроля над обоими аккаунтами и пока не планируется.

На этом этапе не выбираются библиотека входа, схема сессий и формат доступа к NutriFlow. Не создаются собственные токены, парольный вход или временный «вход» через присланный клиентом `userId`.

## Какие данные личные

- Сессия, история сообщений, черновик и вопросы принадлежат одному пользователю.
- Записи дневника наследуют владельца подтверждённой сессии. Подтверждение не может создавать порции другого пользователя.
- Дневная цель относится к паре «пользователь + дата», а не только к дате. У двух людей могут быть разные цели на один день.
- Загруженная фотография этикетки и созданный из неё продукт личные. Непрозрачное имя файла само по себе не защищает фотографию.
- Продукты ручного ввода и личные алиасы продуктов не должны изменять каталог другого человека.
- Будущие рецепты и сохранённые блюда по умолчанию личные; совместный доступ не входит в текущую модель.

Сейчас сервер всегда выбирает одного локального владельца; это не проверка того, кто отправил HTTP-запрос. В будущем многопользовательском режиме владелец должен определяться из проверенного входа, а не из JSON, query string или произвольного заголовка клиента. Тогда чтение, изменение, подтверждение, поиск и выдача файлов должны проверять владельца; знания идентификатора чужой сессии будет недостаточно для доступа.

## Общий и личный каталоги

У продукта в SQLite появился необязательный `UserId`: `null` обозначает общий каталог, UUID — личную запись. Общими сейчас становятся только новые результаты отдельного серверного импорта внешней базы через `ProductLookupService`. Импорт проверяет совпадение штрихкода, `ExternalService` и HTTP(S)-ссылку; существующая проверка полей Open Food Facts остаётся обязательной. Клиент не передаёт признак общего доступа или владельца. Общий доступ не повышает `DataQuality`: данные пользовательской внешней базы остаются с прежней оценкой качества. Демо-продукты сохраняются за локальным владельцем.

Ручной ввод и фотография пользователя не становятся общими автоматически, даже если совпал штрихкод. Личная правка продукта не должна перезаписывать общую запись или правку другого человека. Публикация пользовательских данных и общий редактор каталога не входят в этот шаг.

При поиске учитываются только личные данные текущего пользователя и общий каталог. Для одного штрихкода личная версия имеет приоритет, даже если её качество ниже: это выбор пользователя, а не повышение точности. Поиск по имени или личному алиасу общей записи также возвращает личную версию того же штрихкода без дубля. Совпадение имени у разных продуктов не объединяет их: существующие правила качества и неоднозначности остаются. Чужие личные продукты и алиасы не участвуют даже косвенно.

Штрихкод уникален отдельно в общем каталоге и внутри каталога каждого владельца. Это обеспечивают два фильтрованных уникальных индекса SQLite: один по `Barcode` для общего каталога, другой по `(UserId, Barcode)` для личного. Один nullable-составной индекс не защитил бы общие строки от дублей с `NULL`.

У алиаса обязательный `UserId`, в том числе при ссылке на общий продукт. Пара `(UserId, ProductId, NormalizedName)` уникальна; два человека могут независимо сохранить одинаковый алиас. Улучшение личного продукта и сохранение прежнего имени как алиаса происходят только в пределах владельца, не меняя общий продукт. Общий продукт не может импортироваться из фотографии пользователя или ручного ввода.

## Фотографии этикеток

В SQLite таблица `LabelPhotos` связывает `FileName` с обязательным `UserId` и временем регистрации `RegisteredAtUtc`. Имя файла — глобальный первичный ключ: две записи разных владельцев не могут ссылаться на один физический файл. Внешний ключ с запретом удаления защищает связь с `Users`. Содержимое изображения остаётся на диске; ссылка `label-photo:<имя>` и её формат не меняются.

`LabelPhotoStore` существует в пределах запроса вместе с EF-контекстом. Сначала файл полностью записывается и закрывается, затем сохраняются метаданные. При обычном сбое или отмене удаляется только созданный в этой попытке файл. SQLite и файловая система не образуют общей транзакции: аварийное завершение процесса между записью и регистрацией может оставить недоступный файл без метаданных. Автоматическое присвоение такого файла при чтении запрещено.

Выдача фото и сохранение продукта из этикетки проверяют одновременно запись текущего владельца и существование обычного файла. Чужая / неизвестная фотография возвращает одинаковый `404`; ссылка на неё при создании продукта — `400`, без изменения каталога. Ответы фотографии имеют `Cache-Control: private, no-store`. Принимаются только исторически генерируемые имена: lowercase `Guid:N` и `.jpg`, `.png` или `.webp`. Вложенные пути и символические ссылки не используются.

## Существующие данные

Старые записи были созданы без владельца. Перед миграцией сделаны резервные копии существующей SQLite-базы и фотографий. Миграция создаёт отдельного постоянного локального владельца и относит к нему прежние сессии и дневные цели; записи дневника наследуют владельца своей сессии. Старые данные не переходят первому вошедшему аккаунту автоматически.

Консервативное правило: данные нынешней локальной установки остаются за выделенным локальным владельцем до явно подтверждённого переноса. Миграция каталога относит все старые продукты и алиасы к уже существующему локальному владельцу: даже внешний продукт мог получить личный алиас или правку. Она не создаёт второго владельца и останавливается, если прежний владелец отсутствует. Общий каталог далее наполняется отдельным публичным импортом, не переносом старых личных связей. Подтверждённые порции, их КБЖУ, качество и первоисточники миграция не пересчитывает; фотографии сохраняются отдельно, в том числе ещё не связанные с продуктом.

Миграция применяется при следующем запуске API с включённым `Database:ApplyMigrationsOnStartup`. После обновления схемы `LegacyLabelPhotoImporter` один раз регистрирует допустимые файлы из корня настроенного каталога за `IsLegacyLocal` владельцем, в том числе фотографии, ещё не связанные с продуктом. Строки фотографий и отметка завершения записываются одной транзакцией; отмена откатывает обе части. Уже зарегистрированный файл не меняет владельца. Повторный запуск не присваивает новые неизвестные файлы и не меняет время регистрации прежних.

Перед первым запуском необходимо восстановить и проверить правильные пути к базе и фотографиям вместе. Пустой каталог также помечается импортированным; последующая смена пути не запускает перенос заново. При `Database:ApplyMigrationsOnStartup=false` автоматического импорта нет: для перехода старого хранилища нужен один управляемый запуск с включённой настройкой. Нельзя вручную сбрасывать маркер ради повторного сканирования общей папки.

При перестройке старых таблиц SQLite EF Core предупреждает о не полностью транзакционном участке; резервная копия необходима до запуска. На этой машине проверены миграции отдельной копии базы, а исходный файл не менялся. Обратные миграции каталога и фотографий запрещены: удаление владельцев и отметки переноса могло бы раскрыть личные данные при повторном импорте. Это подготовка хранения, не защита от другого HTTP-клиента. Резервная копия и восстановление должны включать SQLite и каталог фотографий как одну пару.

## Почему Google и Apple отложены

Это обычная интеграционная задача, но не только добавление кнопки: нужны регистрация приложения у провайдера, настройки для выбранного мобильного клиента и проверка полученного подтверждения на сервере. Google описывает настройку приложения и проверку ID token в [документации OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect); Apple требует настройки приложения и соответствующих возможностей в [документации Sign in with Apple](https://developer.apple.com/documentation/signinwithapple/configuring-your-environment-for-sign-in-with-apple).

Пользователь попросил пока не подключать внешний вход при необходимости такой подготовки. Аккаунты и консоли провайдеров не создаются, ключи не запрашиваются. До реализации входа нельзя выдавать проектную модель владельцев за настоящую защиту.

## Проверки перед многопользовательским доступом

Будущая реализация должна подтверждаться тестами двух пользователей:

- первый не видит и не меняет сессии, дневник, цели, продукты, алиасы и фотографии второго;
- одинаковая дата не смешивает цели и прогресс;
- одинаковый штрихкод не объединяет личные правки и источники;
- подмена присланного клиентом идентификатора не меняет владельца;
- запрос без проверенного входа не получает личные данные;
- повторное подтверждение не создаёт дублей внутри дневника владельца;
- существующие данные переживают миграцию без потери подтверждённых КБЖУ и фотографий.

Проверки двух владельцев на уровне хранилищ сессий, целей, дневника, каталога и фотографий реализованы. Для фотографий проверены отказ чужому владельцу, HTTP-выдача и сохранение продукта, прежние ссылки, однократный перенос, перезапуск, сбои и отмена. HTTP-тест второго владельца выбирает его на сервере через тестовую регистрацию сервиса, а не через присланный клиентом ID. Проверки настоящего входа и запросов без него остаются будущим этапом. Идемпотентность создания и дополнения сессии уже реализована отдельно.
